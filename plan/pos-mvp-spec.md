# POS ร้านค้าปลีก: สเปกระบบและแผนส่งมอบรุ่นแรก

วันที่: 20 ตุลาคม 2026 · ฉบับ 0.1 · สถานะ: ฉบับเสนอสำหรับทบทวนก่อนแตกงานพัฒนา

## 1. เป้าหมายและสถานะการตัดสินใจ

สร้าง POS สำหรับใช้ขายจริงในร้านค้าปลีกของเจ้าของซึ่งเป็นนักพัฒนา โดยเริ่มจากระบบขนาดเล็กที่ตรวจยอดเงิน สต๊อก และประวัติการทำรายการได้ เมื่ออินเทอร์เน็ตขัดข้องต้องยังเริ่มระบบและขายเงินสดได้บนเครื่องร้าน

**สิ่งที่ผู้ใช้ยืนยันแล้ว**

- ใช้ขายจริงในร้านค้าปลีกของตนเอง และต้องการทำระบบเอง
- ใช้สถาปัตยกรรมที่ระบบขายหลักและฐานข้อมูลอยู่ในร้าน
- ใช้ cloud สำหรับสำรองข้อมูลเมื่อมีอินเทอร์เน็ต
- ผู้ช่วยรับบท PM และ Lead Dev เพื่อวางขอบเขต ออกแบบ และแบ่งงานพัฒนา

**ข้อเสนอที่ใช้กำหนดขอบเขตเอกสารนี้ ยังไม่ใช่ข้อมูลร้านที่ยืนยันแล้ว**

- หนึ่งร้าน หนึ่งเครื่องขาย ใช้เบราว์เซอร์บนเครื่องเดียวกับ API และฐานข้อมูล
- สินค้านับเป็นจำนวนเต็มหน่วยชิ้น ไม่มีไซซ์/สี ล็อต หมายเลขเครื่อง หรือวันหมดอายุ
- เงินบาท หน่วยคำนวณเป็นสตางค์ หน้าจอภาษาไทย และวันทำการตาม Asia/Bangkok
- รับเงินสดในรุ่นแรก มีบัญชี owner และ cashier เปิด–ปิดกะและนับเงินสด
- ห้ามสต๊อกติดลบ ยกเลิกได้เฉพาะทั้งบิลในกะเดิมที่ยังเปิดอยู่
- ใช้ TypeScript, React, Vite, Fastify, better-sqlite3 และ SQLite ตามข้อเสนอในส่วน 4

การยืนยันสถาปัตยกรรมไม่ได้หมายถึงยืนยันสมมติฐานข้างต้น หากร้านต้องใช้หลายเครื่อง ชั่งน้ำหนัก หรือรับชำระรูปแบบอื่นตั้งแต่วันแรก ต้องปรับขอบเขตก่อนประเมินรอบพัฒนา

## 2. ผลลัพธ์ที่ถือว่าสำเร็จ

1. เปิดเครื่องและเข้าสู่ระบบได้ขณะตัดอินเทอร์เน็ต โดยไม่อาศัยหน้าที่เปิดค้างไว้
2. เปิดกะ รับสินค้าเข้า ขายเงินสด ออกใบเสร็จ ตรวจบิล และปิดกะได้ครบวงจร
3. ยอดขาย เงินสดที่คาดหวัง และสต๊อกตรวจกลับถึงรายการต้นทางได้
4. คำขอซ้ำหรือคำตอบสูญหายไม่สร้างบิล การรับเงิน หรือการตัดสต๊อกซ้ำ
5. สำรองข้อมูลที่สอดคล้องกันได้ และกู้คืนบนเครื่องพร้อมใช้ได้จากการซ้อมจริง
6. ผ่าน pilot ด้วยอุปกรณ์ร้านและข้อมูลที่ตรวจยอดได้ ก่อนใช้เป็นระบบขายหลัก

| --- | --- |
| ผู้ใช้งาน | สร้าง owner ครั้งแรกแบบ local; owner จัดการ cashier; เปิด/ปิดบัญชีและล็อกอินโดยไม่พึ่งบริการภายนอก |
| สินค้า | เพิ่ม/แก้ไขชื่อ SKU ราคาขาย บาร์โค้ดหนึ่งรหัสต่อสินค้า และสถานะจำหน่าย; ค้นหาหรือรับรหัสจากเครื่องสแกนแบบคีย์บอร์ด |
| สต๊อก | รับเข้าและปรับยอดนับจริงพร้อมเหตุผล; แสดงคงเหลือและประวัติ movement; ไม่รวมใบสั่งซื้อหรือเจ้าหนี้ |
| ขาย | ตะกร้า เปลี่ยนจำนวน ตรวจราคา/สต๊อกจาก server รับเงินสด คำนวณทอน และยืนยันบิล |
| ใบเสร็จ | เปิดดูและพิมพ์ผ่าน browser print; พิมพ์ซ้ำจากบิลเดิม; การพิมพ์ล้มเหลวไม่ย้อนการขาย |
| แก้รายการผิด | owner ยกเลิกทั้งบิลในกะเดิมที่เปิดอยู่ พร้อมเหตุผลและยืนยันการคืนเงิน/สินค้าตามข้อ 5 |

ก่อน pilot ต้องตรวจว่าขอบเขตที่แยกออกมีข้อใดเป็นงานประจำที่ร้านขาดไม่ได้ แล้วนำข้อนั้นกลับมาวางแผนก่อนเปิดใช้

## 4. สถาปัตยกรรมและเทคโนโลยีที่เสนอ

```text
เครื่องร้าน
  Browser UI ──same-origin HTTP──> Local API ──> SQLite บนดิสก์เครื่องร้าน
                                       │
                                       └──> Consistent snapshot ──> Backup queue
                                                                         │
                                                        เมื่อออนไลน์ ──> Cloud storage
```

- **แอป:** modular monolith แยกโมดูล auth, catalog, inventory, sales, shifts, reports และ backup ภายในโครงการเดียว
- **UI:** React + TypeScript + Vite; production build ให้ API serve ไฟล์ทั้งหมดจากเครื่องร้าน ไม่ใช้ development server ในการขายจริง
- **API:** Node.js 24.x LTS + Fastify + TypeScript; pin patch และ dependency versions ใน release/lockfile และตรวจ native dependency บนเครื่องเป้าหมาย
- **ฐานข้อมูล:** SQLite ผ่าน better-sqlite3; ใช้ SQL migrations และ prepared statements; มี API เพียงตัวเดียวเป็นผู้เขียนหลัก
- **การทดสอบ:** unit tests สำหรับสูตร/กติกา, integration tests กับ SQLite จริง และ browser tests สำหรับเส้นทางขายหลัก โดยแยกฐานข้อมูลทดสอบจากข้อมูลร้าน
- **ติดตั้ง:** เริ่มจาก local service ที่เปิดอัตโนมัติเมื่อเครื่องเริ่มทำงานและมี shortcut เปิด UI; milestone แรกระบุ OS/เบราว์เซอร์/อุปกรณ์เป้าหมายก่อนสร้างชุดติดตั้ง
- **Cloud:** adapter อัปโหลด backup ไปยัง object storage ที่เลือกใน milestone แรก; ไม่เปิด API ร้านสู่อินเทอร์เน็ตและไม่มีการ merge ข้อมูลกลับจาก cloud

ให้ bind เฉพาะ loopback ในรุ่นแรก ไฟล์ UI ฟอนต์ และส่วนจำเป็นต่อการขายอยู่ local ทั้งหมด ไม่ใช้ cloud login หรือ CDN เป็นเงื่อนไขการขาย การเชื่อม LAN ในอนาคตต้องออกแบบการเข้าถึงและทดสอบเพิ่ม และเครื่องลูกเรียก API แทนการแชร์ไฟล์ฐานข้อมูล

ค่า SQLite ที่เสนอ: `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON` ทุก connection และ `busy_timeout=5000` มิลลิวินาที ธุรกรรมเขียนสั้น ไม่มี network call ภายใน และจัดการ busy/error ให้ผู้ใช้ลองคำขอเดิมได้ การตั้งค่านี้ไม่ใช่สิ่งทดแทน backup หรือการตรวจฮาร์ดแวร์

## 5. กติกาธุรกิจและความถูกต้องของข้อมูล

### R01 — จำนวนเงินและสินค้า

- จำนวนเงินทุก field เป็นจำนวนเต็มหน่วยสตางค์; จำนวนสินค้าเป็นจำนวนเต็มบวก ราคาตั้งแต่ศูนย์ขึ้นไป
- ไม่ใช้ floating point คำนวณยอดเงิน ตรวจขอบเขตจำนวนและผลรวมให้อยู่ใน safe integer ก่อนบันทึก
- รุ่นนี้ไม่มีส่วนลดหรือการคำนวณภาษีแยก ยอดบิลเท่ากับผลรวมราคาขายต่อหน่วยคูณจำนวน ไม่รับยอดจาก client เป็นข้อยุติ
- เงินรับต้องไม่น้อยกว่ายอดบิล เงินทอนเท่ากับเงินรับลบยอดบิล เงินเข้าลิ้นชักจากการขายคือยอดบิลหลังทอน
- SKU ต้องมีและไม่ซ้ำหลัง trim/แปลงเป็น uppercase; บาร์โค้ดถ้ามีต้องไม่ซ้ำและเก็บเป็นข้อความเพื่อรักษาศูนย์นำหน้า

### R02 — สต๊อกและข้อมูลสินค้า

- ยอดตั้งต้น รับเข้า ขาย ยกเลิก และปรับยอด ต้องมี stock movement อ้างอิงเหตุการณ์ ผู้ทำ และเวลา
- คงเหลือเท่ากับผลรวม movement; ถ้ามีตาราง balance ให้เปลี่ยนพร้อม movement ใน transaction เดียว ห้ามแก้ยอดโดยไร้ประวัติ
- ปรับเป็นยอดนับจริงโดยคำนวณส่วนต่างจาก balance ขณะบันทึก พร้อมเหตุผล ไม่ใช้ balance เก่าจากหน้าจอ
- ตะกร้าไม่จองและไม่ตัดสต๊อก การขายที่ของไม่พอถูกปฏิเสธทั้งบิล และคงเหลือต้องไม่ติดลบ
- สินค้าที่เคยใช้ขายให้ปิดจำหน่ายแทนการลบ บิลเก่าเก็บ snapshot ชื่อ SKU ราคา จำนวน และยอดรายการ
- หากราคาตอนยืนยันต่างจากราคาที่แสดงในตะกร้า ให้ส่งข้อผิดพลาด `PRICE_CHANGED` เพื่อให้ผู้ขายตรวจและยืนยันราคาใหม่ ไม่เปลี่ยนยอดเงียบ ๆ

### R03 — ยืนยันการขายและกู้ผลคำขอ

- กำหนด state ของ checkout ฝั่ง UI เป็น draft → submitting → confirmed หรือ unresolved; unresolved ต้องค้นผลเดิมก่อนเริ่มขายซ้ำ
- สร้าง UUID สำหรับ checkout request ก่อนส่ง เก็บ key และ payload ของคำขอที่ยังไม่ทราบผลใน browser จนกู้ผลได้ เพื่อรองรับ reload/restart
- key เดิมและ payload เดิมคืนผลบิลเดิม; key เดิมแต่ payload ต่างกันคืน `409 IDEMPOTENCY_CONFLICT` โดยไม่มีผลทางธุรกิจเพิ่ม
- ตรวจ idempotency ที่บันทึกไว้ก่อนตรวจราคาหรือสต๊อกใหม่ของคำขอซ้ำ เพื่อคืนผลเดิมแม้ข้อมูลสินค้าถูกแก้แล้ว
- ตรวจผู้ใช้ กะ ราคา สต๊อก และบันทึก sale, sale lines, cash payment, stock movements, balance, audit และผล idempotency ใน transaction เดียว
- เมื่อ commit แล้วถือว่าขายสำเร็จ แม้ HTTP response หรือการพิมพ์หายไป; คำขอซ้ำต้องเข้าถึงผลที่ commit แล้วได้
- แสดงความสำเร็จเมื่อยืนยันการบันทึกได้เท่านั้น กรณีไม่ทราบผลให้แสดงสถานะชัดและใช้ key เดิมตรวจ/ลองใหม่
- คำสั่งรับ/ปรับสต๊อก เงินนำเข้า/ออก void และเปิด/ปิดกะต้องใช้ request key และบันทึกผลใน transaction เช่นเดียวกัน เพื่อไม่เพิ่ม movement หรือยอดเงินซ้ำเมื่อส่งคำขอใหม่หลังคำตอบสูญหาย
- sale มี UUID ถาวรและเลขบิลที่ไม่ซ้ำ; รูปแบบเลขบิลใช้ `POS1-` ตามด้วย UUID แบบตัดขีดออก เพื่อไม่พึ่งการนับแถวหรือรีเซ็ตลำดับหลัง restore

### R04 — ยกเลิกทั้งบิล

- อนุญาตเฉพาะ owner สำหรับบิลเงินสดในกะปัจจุบันที่ยังเปิดอยู่และยังไม่เคยยกเลิก
- owner ต้องระบุเหตุผล ยืนยันคืนเงินสดครบตามยอดบิล และยืนยันสินค้ากลับมาครบในสภาพจำหน่ายได้หรือยังไม่ได้ส่งมอบ
- เก็บบิลเดิมและสร้าง void record, cash reversal, stock movements กลับยอด และ audit ใน transaction เดียว ห้ามแก้ทับหรือลบประวัติเดิม
- void record อ้างอิง sale แบบ unique; แม้ส่งซ้ำด้วย request key ใหม่ ต้องไม่คืนเงินในข้อมูลหรือตัดกลับสต๊อกซ้ำ
- void เป็นการบันทึกสิ่งที่ผู้ปฏิบัติงานทำจริง ไม่ได้โอนคืนเงินให้อัตโนมัติ
- การคืนบางชิ้น สินค้าเสียหาย หรือคืนหลังปิดกะต้องใช้ return workflow เพิ่มเติม หากเป็นงานจำเป็นของร้านให้เพิ่มก่อน pilot

### R05 — กะและรายงาน

- เปิดได้หนึ่งกะต่อร้านในเวลาเดียวกัน; ทุก sale, void และรายการเงินนำเข้า/ออกต้องผูกกะที่เปิดอยู่
- เงินสดคาดหวัง = เงินตั้งต้น + ยอดบิลขายทั้งหมดในกะ − ยอดยกเลิกในกะ + เงินนำเข้า − เงินนำออก
- เงินขาด/เกิน = เงินนับจริง − เงินสดคาดหวัง; เงินนำเข้า/ออกไม่ใช่ยอดขาย และไม่หักยอดยกเลิกซ้ำจากบิลที่กรองออกแล้ว
- ปิดกะต้องเก็บยอดคาดหวัง ยอดนับจริง ส่วนต่าง ผู้ปิด และเวลาเป็น snapshot; ปิดซ้ำคืนผลเดิมและกะปิดแล้วแก้ไม่ได้
- การขายกับปิดกะที่เกิดพร้อมกันต้องเรียงด้วย transaction: การขายอยู่ในกะก่อนปิด หรือถูกปฏิเสธทั้งรายการ
- รายงานรายวันจัดกลุ่มจากเวลาของ server ตาม Asia/Bangkok; เก็บ timestamp ใน UTC และแยกรายงานกะที่คร่อมเที่ยงคืนออกจากยอดตามวัน

### R06 — สิทธิ์และ audit

- cashier ค้นสินค้า เปิดกะ ขาย ดู/พิมพ์บิล และปิดกะได้; owner เพิ่มสิทธิ์จัดการสินค้า ผู้ใช้ สต๊อก void เงินนำเข้า/ออก และ backup settings
- ตรวจสิทธิ์ใน API ทุกคำขอ บันทึกผู้ทำจริง ไม่อาศัยการซ่อนปุ่มอย่างเดียว
- สร้าง owner ผ่านขั้นตอน setup บนเครื่องครั้งแรก ไม่มี username/password เริ่มต้นที่ใช้ร่วมกัน
- เก็บ password hash แบบ Argon2id อย่างน้อย memory 19 MiB, iterations 2, parallelism 1 พร้อม salt จากไลบรารี และจำกัดการลองล็อกอิน
- ใช้ session ฝั่ง server และ cookie แบบ HttpOnly/SameSite=Strict; ตรวจ Host/Origin สำหรับ API ที่เปลี่ยนข้อมูล จำกัด request ให้มาจาก UI ของแอป
- audit อย่างน้อยการแก้ราคา รับ/ปรับสต๊อก void เงินนำเข้า/ออก ปิดกะ เปลี่ยนสิทธิ์ และ restore โดยไม่บันทึกรหัสผ่าน/session token/cloud secret ลง log

## 6. ขอบเขตข้อมูลหลัก

| กลุ่มข้อมูล | หน้าที่และข้อผูกพัน |
| --- | --- |
| users / sessions | บัญชี สิทธิ์ hash และ local sessions; ปิดบัญชีไม่ลบผู้ทำรายการเก่า |
| products | SKU/บาร์โค้ด/ชื่อ/ราคาปัจจุบัน/สถานะจำหน่าย |
| inventory_balances / stock_movements | ยอดปัจจุบันและเหตุการณ์เปลี่ยนยอด; movement ทุกตัวมีต้นทางและผู้ทำ |
| shifts / cash_movements | เงินตั้งต้น เงินนำเข้า/ออก ยอดนับปิดกะ และผลต่าง |
| sales / sale_items / payments | ข้อเท็จจริงขณะขาย รวม tendered/change; ตัวเลขที่ขายสำเร็จแล้วแก้ไม่ได้ |
| sale_voids / payment_reversals | กลับยอดทั้งบิลแบบอ้างอิงต้นทาง พร้อมผู้อนุมัติและเหตุผล |

ใช้ constraints สำหรับ unique key, foreign key และค่าจำนวน/เงินที่ถูกต้อง โดยเก็บสำเนาราคาหรือชื่อขณะขายไว้กับบิล ไม่อ่านค่าปัจจุบันมาย้อนเขียนประวัติ

## 7. Backup, restore และเหตุขัดข้อง

### R07 — การสำรอง

- สร้าง consistent snapshot ผ่าน SQLite backup API ทุก 15 นาทีขณะระบบทำงาน และหลังปิดกะ ไม่ copy เฉพาะไฟล์ `.db` ที่กำลังใช้งานแบบทั่วไป
- แต่ละ snapshot มี app/schema version, เวลาสำรอง และ checksum; อัปโหลดผ่าน TLS ไปยัง private cloud storage ที่เปิด encryption at rest และใช้ credentials จำกัดเฉพาะพื้นที่ backup
- เก็บ snapshot ระยะสั้น 48 ชั่วโมง และ daily snapshot 30 วัน ทั้งนี้ต้องตรวจพื้นที่/ค่าใช้จ่ายจากข้อมูลจริงก่อน pilot
- upload ล้มเหลวให้ค้างงานและ retry ด้วย backoff ไม่ขวางการขาย; ถ้างานรายรอบตกค้างให้ส่งจุดกู้คืนล่าสุดก่อน และรักษา daily snapshots ตาม retention
- แสดงเวลา snapshot ล่าสุด เวลา cloud backup สำเร็จล่าสุด งานที่ค้าง และข้อผิดพลาดจริง ไม่ถือว่าตั้งเวลาแล้วเท่ากับสำรองสำเร็จ
- ไม่รวม credentials ไว้ในไฟล์ snapshot; มีขั้นตอนเจ้าของเข้าถึง cloud และกู้คืน settings บนเครื่องใหม่ได้
- **เป้าหมาย RPO:** จุดกู้คืน cloud ตามหลังข้อมูลไม่เกิน 30 นาที เมื่อเครื่อง เน็ต และปลายทางทำงานปกติ; เมื่อ offline ให้แสดงอายุจุดกู้คืนจริง โดยไม่รับประกันกรอบนี้
- สำเนาบนดิสก์เดียวกันไม่ครอบคลุมดิสก์เสีย หากต้องจำกัดการสูญเสียระหว่าง offline ต้องสำรองลงสื่ออีกชิ้นหนึ่งด้วยและทดสอบก่อน pilot

### R08 — การกู้คืนและอัปเกรด

- restore เป็นงานของ owner/ผู้ดูแลใน maintenance mode หยุดการขายและยืนยันว่ามีเครื่อง authoritative ทำงานเพียงชุดเดียว
- เก็บสำเนาข้อมูลเดิม ตรวจ checksum/schema compatibility และกู้ลงตำแหน่งสะอาดก่อนสลับใช้งาน ตรวจ integrity, จำนวนบิล, ยอดรวม และข้อมูลล่าสุดเทียบ manifest
- หลัง restore บังคับล็อกอินใหม่ และคง UUID/เลขบิลเดิมทั้งหมด; บิลที่อยู่นอกจุดกู้คืนอาจหาย ต้องตรวจใบเสร็จ/ยอดเงินจริงและกระทบยอดก่อนกลับมาขาย
- **เป้าหมาย RTO:** กลับมาใช้งานภายใน 2 ชั่วโมงเมื่อมีเครื่องทดแทนพร้อมและ backup ที่ใช้ได้; จับเวลาจากการซ้อมก่อน pilot ไม่รวมเวลาจัดหาฮาร์ดแวร์
- ก่อน migration ให้สำรองและทดสอบกับสำเนาข้อมูล เปลี่ยนรุ่นในช่วงปิดร้าน พร้อมขั้นตอนถอยกลับที่รองรับ schema เดิม ห้าม rollback เพียงไฟล์โปรแกรมถ้า schema ไม่เข้ากัน
- เน็ตล่มให้ขายเงินสดต่อได้; cloud ล่มให้รอ upload; เครื่องหลักหรือดิสก์เสียให้หยุดใช้เครื่องนั้นและเข้า restore runbook
- กำหนดวิธีสำรองการขายขณะเครื่องหลักใช้งานไม่ได้กับเจ้าของใน milestone แรก โดยห้ามเปิดฐานข้อมูลสำเนาหลายชุดขายคู่กันแล้วนำมารวมโดยไร้ workflow
- ถ้าดิสก์เต็มหรือ transaction ล้มเหลว ต้องไม่แสดงขายสำเร็จหรือรับรายการใหม่แบบค้างบางส่วน และต้องกู้สถานะคำขอเดิมก่อนลองใหม่

## 10. เกณฑ์เปิด pilot และวิธีทำงานร่วมกัน

**ก่อนเปิด pilot**

- ผ่าน A01–A16 ด้วยฐานข้อมูลทดสอบ และทดสอบ integration บนอุปกรณ์เป้าหมาย
- ใช้ข้อมูลตัวอย่างอย่างน้อย 10,000 สินค้าและ 100,000 บิลวัดเวลาค้นหา/checkout พร้อม backup; เป้าหมาย p95 ค้นหาต่ำกว่า 300 ms และยืนยันบิลต่ำกว่า 1 วินาทีบนเครื่องเป้าหมาย โดยไม่รวมการพิมพ์
- ทดลอง scanner/printer จริง หากใช้ browser print ต้องยอมรับขั้นตอนเลือกเครื่องพิมพ์/กดพิมพ์ของ OS; เครื่องพิมพ์อัตโนมัติแบบไม่มี dialog ต้องเพิ่ม scope
- ซ้อม restore มีบันทึกจุดกู้คืนและเวลาที่ใช้; เจ้าของเข้าถึง backup/credentials และทำตาม runbook ได้
- ทดลองครบอย่างน้อยหนึ่งวันทำการด้วยข้อมูลที่ตรวจยอดได้ เงินสด รายงาน และสต๊อกตรงกัน หรือมีส่วนต่างที่บันทึกเหตุผลและยอมรับได้
- ระบุผู้ดูแล เครื่องสำรอง/วิธีขายฉุกเฉิน และขั้นตอนกระทบยอดก่อนกลับมาใช้งาน ไม่มีปัญหายอดผิด ข้อมูลซ้ำ ข้อมูลหาย หรือสิทธิ์ที่ยังไม่แก้

**การแบ่งบทบาท**

- เจ้าของ/Dev owner: ยืนยันกติกาของร้านและอุปกรณ์ ทดลอง workflow ตรวจยอด และตัดสินใจเปิดใช้จริง
- ผู้ช่วย PM: ดูแล scope, backlog, dependencies, เกณฑ์รับงาน ความเสี่ยง และอัปเดตประมาณการจากงานที่เสร็จจริง
- ผู้ช่วย Lead Dev: ออกแบบโมดูล/ข้อมูล/contracts วางแผน transaction และ recovery ช่วยพัฒนา ตรวจโค้ด และตรวจหลักฐานการทดสอบ

หลังผู้ใช้ทบทวนสเปกฉบับนี้ ขั้นถัดไปคือเขียน implementation plan ที่ระบุโครงไฟล์ interfaces งานย่อย และคำสั่งตรวจรับ แล้วทบทวนแผนนั้นก่อนเริ่มสร้างระบบ

## 11. แหล่งอ้างอิงประกอบการออกแบบ

แหล่งข้อมูลด้านล่างรองรับคุณสมบัติ/ข้อจำกัดของเครื่องมือ ส่วนขอบเขต กติกาธุรกิจ ค่าเป้าหมาย และประมาณการเป็นข้อเสนอออกแบบของโครงการนี้

- [SQLite: Appropriate Uses](https://www.sqlite.org/whentouse.html) — local storage และข้อจำกัดการเปิดไฟล์ฐานข้อมูลตรงจากหลายเครื่อง
- [SQLite: PRAGMA](https://www.sqlite.org/pragma.html) — WAL, synchronous, foreign keys และ busy timeout
- [SQLite: Online Backup API](https://sqlite.org/backup.html) — consistent snapshot ของฐานข้อมูลที่กำลังใช้งาน
- [better-sqlite3: API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md) — transaction และ backup interface
- [Node.js: Releases](https://nodejs.org/en/about/previous-releases) — เลือก runtime สาย LTS สำหรับ production
- [Fastify: LTS](https://github.com/fastify/fastify/blob/main/docs/Reference/LTS.md) และ [Vite: Getting Started](https://vite.dev/guide/) — ตรวจ Node compatibility ก่อน pin dependencies
- [OWASP: Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) — Argon2id และการเก็บ password hash
