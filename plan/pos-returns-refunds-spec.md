# POS โมดูลคืนสินค้าและคืนเงินสด

วันที่: 21 ตุลาคม 2026 · ฉบับ 0.1 · สถานะ: สเปกสำหรับทบทวนก่อนแตกงานพัฒนา

เอกสารนี้ขยาย [สเปก POS MVP](pos-mvp-spec.md) เฉพาะการคืนสินค้าจากบิลเดิมและคืนเงินสด **บางรายการหรือทั้งบิล** รวมถึงการคืนหลังปิดกะเดิม ใช้แอปและฐานข้อมูลเดียวกับ POS ไม่ใช่ระบบใหม่แยกต่างหาก กติกานี้แทนข้อความในสเปก MVP ที่เคยเลื่อนการคืนบางรายการและคืนข้ามกะไปเป็นรุ่นถัดไป ส่วนการยกเลิกบิล (`void`) ในกะเดิมยังเป็น workflow คนละประเภท

## 1. เป้าหมายและขอบเขต

เจ้าของร้านต้องค้นบิลเงินสดเดิม เลือกจำนวนที่จะรับคืน จ่ายเงินตามราคาที่ขายจริง และเลือกว่าสินค้าที่รับคืนขายต่อได้หรือเสียหาย โดยเงินสด สต๊อก และรายงานตรวจย้อนถึงบิลและรายการคืนได้ แม้คืนต่างวันหรือส่งคำขอซ้ำ

รุ่นแรกของโมดูลนี้รองรับหนึ่งร้าน หนึ่งลิ้นชักเงิน เงินบาท สินค้าจำนวนเต็ม และบิลที่ชำระเงินสดเต็มจำนวนตามขอบเขต POS หลัก `owner` เท่านั้นที่ยืนยันคืนได้ ต้องมีกะปัจจุบันเปิดอยู่เพื่อจ่ายเงินคืน

**ไม่รวม:** เคลมกับผู้ผลิต/ซัพพลายเออร์, เปลี่ยนสินค้า, เครดิตร้าน, คืนผ่านบัตรหรือ QR, คืนโดยไม่มีบิล, เงินคืนที่ตกลงต่างจากราคาขาย, คืนค่าจัดส่ง/ค่าธรรมเนียม, สินค้าชั่งน้ำหนัก, ส่วนลดหรือภาษีแยก และเอกสารภาษีเฉพาะรูปแบบ หากจะเพิ่มสิ่งเหล่านี้ต้องออกกติกาเงินและเอกสารใหม่ก่อนพัฒนา

ไม่มีการบังคับจำนวนวันคืนในระบบรุ่นนี้ เจ้าของร้านใช้ข้อกำหนดร้านของตนพิจารณาก่อนอนุมัติ ระบบแสดงวันที่บิลต้นทางเสมอ

## 2. การตัดสินใจออกแบบ

- เก็บ **return/refund เป็นธุรกรรมใหม่** อ้างอิง `sale` และ `sale_line` เดิม ไม่แก้ยอดขายหรือรายการสินค้าในบิลต้นทาง สถานะ `ยังไม่คืน / คืนบางส่วน / คืนครบ` คำนวณจากรายการคืนที่บันทึกแล้ว
- หนึ่งบิลคืนหลายครั้งได้จนกว่าจะครบจำนวนแต่ละรายการ แต่จำนวนคืนสะสมต้องไม่เกินจำนวนที่ขาย
- จำนวนเงินคืนต่อรายการ = `จำนวนคืน × ราคาต่อหน่วยใน sale_line snapshot` หน่วยสตางค์ คำนวณฝั่ง API จากข้อมูลเดิม ไม่รับราคาหรือยอดรวมจาก UI เป็นข้อยุติ สินค้าราคา 0 คืนจำนวนได้โดยยอดเงินคืนเป็น 0
- แต่ละรายการคืนแยกจำนวน `ขายต่อได้` กับ `เสียหาย/ขายต่อไม่ได้` ผลรวมต้องเท่าจำนวนคืน เพิ่มสต๊อกเฉพาะส่วนที่ขายต่อได้ ส่วนเสียหายมีหลักฐานใน return line โดยไม่เพิ่มสต๊อก
- รายการคืนผูกกับ **กะที่จ่ายเงินจริง** และเวลาคืนปัจจุบัน กะของบิลต้นทางไม่เปลี่ยน หากกะเก่าปิดไปแล้ว snapshot และส่วนต่างของกะนั้นต้องไม่เปลี่ยน
- เงินคืนเป็นรายการเฉพาะใน refund ledger ไม่บันทึกซ้ำเป็น `cash out` ทั่วไป เพราะจะหักเงินคาดหวังสองครั้ง ระบบบันทึกการยืนยันว่าจ่ายเงินจริง แต่ไม่ได้สั่งจ่ายธนบัตรทางกายภาพ
- `void` ยังใช้เฉพาะการยกเลิกทั้งบิลตามกติกาเดิม บิลที่ `void` แล้วคืนไม่ได้ และบิลที่มี return อย่างน้อยหนึ่งครั้ง `void` ไม่ได้ ห้ามลบหรือแก้ return เดิมผ่านแอปในรุ่นนี้

## 3. ขั้นตอนใช้งาน

1. `owner` เปิดหน้า **คืนสินค้า** และค้นบิลด้วยเลขบิลตามการค้นของ POS เลือกบิลที่ยังไม่ `void` ระบบแสดงชื่อสินค้า SKU ราคา ณ วันขาย จำนวนซื้อ จำนวนคืนแล้ว และจำนวนที่ยังคืนได้
2. เลือกจำนวนคืนต่อรายการเป็นจำนวนเต็มบวกไม่เกินคงสิทธิ์ แบ่งจำนวนขายต่อได้และเสียหาย ระบุเหตุผล ระบบแสดงยอดคืนและกะที่กำลังเปิด
3. ตรวจเงินสดที่จะจ่ายและยืนยันว่า **จ่ายเงินสดให้ลูกค้าแล้ว** ก่อนบันทึก หากไม่ทราบผลหลังส่ง ให้ตรวจด้วย request key เดิมก่อนเริ่มรายการใหม่
4. เมื่อบันทึกสำเร็จ แสดงเลขเอกสารคืน ยอดเงิน รายการสินค้า สภาพสินค้า ผู้อนุมัติ เวลา เลขบิลต้นทาง และกะที่จ่าย เปิดดู/พิมพ์ซ้ำเอกสารเดิมได้โดยไม่สร้างคืนเงินซ้ำ
5. ประวัติบิลแสดงยอดคืนสะสมและลิงก์รายการคืนทุกครั้ง รายงานกะและวันแสดงยอดคืนแยกจากยอดยกเลิก

ก่อนยืนยัน UI แสดงยอดเงินสดคาดหวังหลังคืน แต่ตัวเลขนี้ไม่ยืนยันว่าลิ้นชักมีธนบัตรจริง หากเงินสดไม่พอ ผู้ปฏิบัติงานต้องจัดเงินและบันทึก `cash in` ตามเหตุการณ์จริงก่อนยืนยันคืน

## 4. กติกาธุรกิจและ invariants

| รหัส | กติกา |
| --- | --- |
| RT01 | คืนได้เฉพาะบิลเงินสดที่มีอยู่และยังไม่ `void` โดย `owner` ที่ยังใช้งานอยู่ พร้อมกะปัจจุบันที่เปิดอยู่ |
| RT02 | `refundableQty(line) = soldQty(line) − Σ returnedQty(line)` ต้องไม่ติดลบ ตรวจใหม่ใน transaction ตอนบันทึก ไม่ใช้ตัวเลขค้างจาก UI |
| RT03 | ทุก return มีอย่างน้อยหนึ่ง line; แต่ละ line อ้างอิง sale line ของบิลนั้น จำนวนคืนเป็นจำนวนเต็มบวก และ `restockQty + damagedQty = returnedQty` โดยทั้งสองจำนวนไม่ติดลบ |
| RT04 | `refundAmount = Σ (returnedQty × originalUnitPriceCents)` ตรวจ safe integer ทุกขั้น ห้ามรับยอดเงินที่ client คำนวณเป็นข้อยุติ |
| RT05 | ต้องมีเหตุผล, owner และ `cashPaidConfirmed=true` การ commit และการจ่ายเงินจริงเป็นคนละเหตุการณ์ จึงต้องมีกระบวนการกระทบยอดเมื่อเครื่องขัดข้อง |
| RT06 | บันทึก return header/lines, refund ledger, stock movements เฉพาะส่วนขายต่อได้, stock balance, audit และ idempotency result ใน SQLite transaction เดียว ผิดพลาดแล้วต้องไม่มีข้อมูลบางส่วน |
| RT07 | request key เดิม + payload เดิมให้ผลรายการเดิม; key เดิม + payload ต่างกันคืน `409 IDEMPOTENCY_CONFLICT` การส่ง key ใหม่เพื่อคืนเกินจำนวนต้องถูกปฏิเสธ |
| RT08 | บิลที่มี return แล้วห้าม `void`; บิล `void` แล้วห้าม return แม้คำขอสองแบบวิ่งชนกัน ต้องสำเร็จได้อย่างใดอย่างหนึ่งเท่านั้น |
| RT09 | เอกสารคืนและบิลต้นทางเป็น append-only จากมุมมองแอป การเปลี่ยนราคาหรือชื่อสินค้าภายหลังไม่เปลี่ยนยอดหรือ snapshot |
| RT10 | ทุก stock movement จากการคืนอ้างอิง return line หรือ return id ตรวจย้อนกลับได้ |

หลัง commit แต่ HTTP response หาย UI ต้องใช้ key เดิมอ่านผลหรือส่งซ้ำก่อนอนุญาตให้เริ่มคำขอใหม่ การพิมพ์ล้มเหลวไม่ยกเลิก return และพิมพ์ซ้ำจากข้อมูลเดิมได้

## 5. โมเดลข้อมูลและ API ที่เสนอ

สคีมาบน production stack ของ [แผนเตรียมระบบขายจริง](production-readiness.md) ใช้ UUID ถาวรและจำนวนเงิน integer หน่วยสตางค์:

| ตาราง | ฟิลด์สำคัญ | ข้อบังคับ |
| --- | --- | --- |
| `returns` | `id`, `return_no`, `sale_id`, `refund_shift_id`, `created_at_utc`, `owner_id`, `reason`, `refund_total_cents` | FK ไป sale/shift/user; เลขเอกสารไม่ซ้ำ; `refund_total_cents >= 0` |
| `return_lines` | `id`, `return_id`, `sale_line_id`, `quantity`, `restock_quantity`, `damaged_quantity`, `original_unit_price_cents`, `refund_line_total_cents` | FK; `UNIQUE(return_id, sale_line_id)`; CHECK จำนวนและผลรวมสภาพสินค้า |
| `cash_refunds` | `id`, `return_id`, `shift_id`, `amount_cents`, `confirmed_by`, `created_at_utc` | `UNIQUE(return_id)`; FK; เงินคืนผูกกะเดียวกับ return; รวมยอดในรายงานเพียงที่นี่ |
| `stock_movements` | เพิ่มชนิด `return_restock`, `reference_return_line_id`, จำนวนบวก | สร้างเฉพาะ `restock_quantity > 0`; ปรับ balance ใน transaction เดียว |
| `idempotency_requests` / `audit_log` | ใช้โครงเดิม เพิ่ม action `return` และเหตุการณ์ `RETURN_CREATED` | เก็บ payload hash/result และ actor เพื่อ replay/ตรวจสอบ |

FK/CHECK ป้องกันข้อมูลพื้นฐาน แต่ยอดคืนสะสมข้ามหลาย return ต้องตรวจภายใน write transaction เดียวกับการ insert เพราะ CHECK รายแถวไม่ครอบคลุม aggregate ต้องทดสอบคำขอสองรายการคืนชนกันด้วย SQLite จริง

API ที่เสนอ (ปรับชื่อ route ให้ตรง convention ของ API หลักเมื่อเริ่มพัฒนา):

| Endpoint | หน้าที่ |
| --- | --- |
| `GET /api/sales/{saleId}/returnable` | ข้อมูลบิลและจำนวนที่ยังคืนได้ พร้อมสถานะ void/คืนสะสม |
| `POST /api/returns` | ส่ง `{requestKey, saleId, lines:[{saleLineId, quantity, restockQuantity, damagedQuantity}], reason, cashPaidConfirmed}`; server ระบุ owner และ shift จาก session/current shift |
| `GET /api/returns/{returnId}` | ดูเอกสารคืนสำหรับประวัติและพิมพ์ซ้ำ |
| `GET /api/requests/{requestKey}` | ใช้ช่องทางกู้ผลคำขอเดิมของ POS โดยจำกัดสิทธิ์เข้าถึงตามผู้ทำรายการ |

ข้อผิดพลาดที่ UI ต้องแสดงให้แก้ถูกจุด: `SALE_NOT_FOUND`, `SALE_VOIDED`, `NO_OPEN_SHIFT`, `FORBIDDEN`, `INVALID_RETURN_LINE`, `RETURN_QUANTITY_EXCEEDED`, `CASH_CONFIRMATION_REQUIRED`, `IDEMPOTENCY_CONFLICT`, `VOID_BLOCKED_BY_RETURN` และข้อผิดพลาดการบันทึก/พื้นที่ดิสก์ตาม POS หลัก คำขอที่ไม่ผ่านต้องไม่บันทึกเงินหรือสต๊อกบางส่วน

## 6. สูตรเงินสดและรายงาน

**รายงานกะ:**

```text
เงินสดคาดหวัง = เงินตั้งต้น
                + ยอดขายเงินสดในกะ
                − ยอด void ที่เกิดในกะ
                − ยอดคืนเงินสดที่เกิดในกะ
                + เงินนำเข้า − เงินนำออก
ส่วนต่าง = เงินนับจริง − เงินสดคาดหวัง
```

ยอดขาย ยอด void และยอดคืนเป็นคนละคอลัมน์ `netSales = grossSales − voids − refunds` ยอดสุทธิของวันหรือกะอาจติดลบเมื่อคืนของบิลเก่า **ห้าม** ย้ายยอดคืนไปหักกะหรือวันขายเดิม รายงานกะปิดแล้วเป็น snapshot ไม่คำนวณใหม่จาก return ที่เกิดภายหลัง

**รายงานรายวัน:** จัดวันจากเวลาที่เกิดแต่ละเหตุการณ์ใน `Asia/Bangkok`: sale ตามเวลาขาย, void ตามเวลายกเลิก, return ตามเวลาคืน แสดงยอดขายรวม ยอดยกเลิก ยอดคืน ยอดสุทธิ และจำนวนธุรกรรมแยกกัน หากกะคร่อมเที่ยงคืน สรุปกะใช้ `shift_id` ส่วนรายวันใช้วันของเหตุการณ์

ตัวอย่าง: ขายสินค้า 2 ชิ้น ชิ้นละ 35 บาทในกะ A ได้ยอดขาย 70 บาท ปิดกะ A แล้ว วันถัดมาเปิดกะ B คืน 1 ชิ้นที่ขายต่อได้: เกิด return 35 บาทในกะ B, สต๊อก +1, กะ A และรายงานวันขายเดิมไม่เปลี่ยน หากคืนอีก 1 ชิ้นแบบเสียหายในกะ B: คืนเพิ่ม 35 บาท แต่สต๊อกไม่เพิ่มอีก ยอดคืนสะสม 70 บาท และบิลมีสถานะคืนครบ

## 7. ความขัดข้องและการปฏิบัติงาน

- **เงินจ่ายแล้วแต่ผลบันทึกไม่ชัด:** เก็บ request key/payload ของรายการค้างข้าม reload ตรวจผลเดิมก่อนทำอะไรเพิ่ม ถ้ายืนยันได้ว่าไม่มีการ commit จึง retry ด้วย key เดิม ห้ามจ่ายซ้ำระหว่างตรวจสอบ
- **commit แล้วแต่ยังไม่ได้จ่ายจริงเพราะเหตุขัดข้อง:** ระบบไม่สามารถตรวจธนบัตรได้ เจ้าของต้องกระทบยอดเอกสารคืนกับเงินในลิ้นชักและบันทึก incident; รุ่นนี้ไม่มีฟังก์ชันย้อน return อัตโนมัติ ต้องกำหนดขั้นตอนแก้ไขที่ audit ได้ก่อนใช้งานจริง
- **สต๊อกไม่ตรงสภาพจริง:** อย่าตั้ง `restock_quantity` ให้สินค้าที่ขายต่อไม่ได้ หากพบภายหลัง ให้ใช้ stock adjustment พร้อมเหตุผลและอ้างอิงเอกสารคืน ไม่แก้ return เดิม
- **backup/restore:** return, refund ledger, movement, request result และ audit ต้องอยู่ใน snapshot เดียวกัน หลัง restore ตรวจรายการคืนล่าสุดควบคู่กับบิลและเงินสดที่จ่ายจริง เพราะธุรกรรมหลังจุดกู้คืนอาจหาย
- **offline:** POS local API/SQLite ต้องทำรายการคืนได้โดยไม่พึ่ง cloud เช่นเดียวกับการขาย; `mockup/` ใช้ `localStorage` เพื่อทดลอง flow เท่านั้น ไม่ใช่หลักฐานความทนทานสำหรับร้านจริง

## 8. ลำดับส่งมอบและเกณฑ์ตรวจรับ

1. ทดลอง flow ใน mockup เดิม: เพิ่มหน้าคืนสินค้า เอกสารคืน ยอดคืนสะสม movement/รายงาน และ migration ของข้อมูลตัวอย่าง `version: 1` ที่บันทึกใน `localStorage` โดยไม่ล้างข้อมูลผู้ใช้เงียบ ๆ ขั้นนี้ใช้ทบทวน UX และกติกาเท่านั้น
2. เมื่อ production POS หลักมี API/SQLite ตาม M2–M4 แล้ว จึงเพิ่ม schema migration, transactional return service, API, สิทธิ์, UI และเอกสารพิมพ์ โดยไม่ใช้ `localStorage` เป็นฐานข้อมูลจริง
3. ทดสอบ integration กับ SQLite จริงและ browser flow บนเครื่องร้าน รวมการส่งซ้ำ, สองคำขอชนกัน, ปิดกะชน return, disk failure, response หาย, พิมพ์ล้มเหลว และ restore
4. Pilot ด้วยบิลและจำนวนเงินตรวจนับได้ก่อนเปิดให้คืนเงินจริงในร้าน

| กรณีตรวจรับ | ผลที่ต้องได้ |
| --- | --- |
| คืน 1 จาก 2 ชิ้นราคา 35 บาท | คืน 35 บาท, บิลเหลือสิทธิ์ 1 ชิ้น, สต๊อกเพิ่มตาม `restock_quantity` เท่านั้น |
| คืนส่วนที่เหลือด้วย key ใหม่ | คืนเพิ่มได้ 35 บาทครั้งเดียว บิลสถานะคืนครบ; ขอเกินอีก 1 ชิ้นถูกปฏิเสธโดยไม่มีผลเงิน/สต๊อก |
| คืนทั้งบิลหลายสินค้าในคำขอเดียว | ยอดคืนเท่าผลรวมราคาในบิลเดิม, ทุก line คงสิทธิ์ 0, เอกสารคืนหนึ่งใบ |
| ราคาสินค้าเปลี่ยนหลังขาย | ใช้ราคา snapshot ใน sale line เดิม ไม่ใช้ราคาปัจจุบัน |
| คืนต่างกะ/ต่างวัน | หักเงินกะและวันที่จ่ายคืน กะเก่าที่ปิดแล้วคง snapshot เดิม |
| ของเสียหายทั้งหมดหรือบางส่วน | เงินคืนเต็มตามจำนวนที่รับคืน แต่สต๊อกเพิ่มเฉพาะจำนวนขายต่อได้ |
| ส่งคำขอซ้ำ key/payload เดิม; key เดิม payload ต่าง | กรณีแรกคืนผลเดิมโดยไม่มีรายการใหม่; กรณีหลัง conflict โดยไม่มีผลใหม่ |
| คืนกับ `void` แข่งกัน; คืนบิล `void` | สำเร็จได้ทางเดียว อีกทางถูกปฏิเสธ; ไม่มี refund/stock movement ซ้ำ |
| cashier เรียก API คืนตรง; ไม่มีการเปิดกะ | ถูกปฏิเสธ และไม่มีข้อมูลธุรกิจเปลี่ยน |
| กะ B เปิดต้น 1,000 บาท ขาย 700, void 200, คืนบิลเก่า 35, นำเข้า 100, นำออก 50 | เงินสดคาดหวัง 1,515 บาท; หากนับได้ 1,505 บาท ส่วนต่าง −10 บาท |
| บันทึกไม่สำเร็จ/response สูญหาย/พิมพ์ล้มเหลว | ไม่มีรายการบางส่วน; กู้ผลด้วย key เดิม; พิมพ์ซ้ำไม่จ่ายเงินหรือเพิ่มสต๊อกซ้ำ |

**เกณฑ์พร้อมใช้จริง:** เงินและจำนวนคืนถูกต้อง, สิทธิ์ฝั่ง API บังคับได้, ทุกธุรกรรม atomic/idempotent, รายงานกะและวันกระทบยอดกับ ledger ได้, และเจ้าของร้านทดลองขั้นตอนจัดการกรณีเงินจ่ายจริงแต่ข้อมูลไม่ชัด ทั้งหมดต้องผ่านบน production stack และอุปกรณ์ร้านจริง ไม่ใช่เฉพาะ mockup
