# แผนพัฒนา POS จาก mockup ไปสู่ระบบขายจริง

เอกสารนี้แปลง [สเปก POS MVP](pos-mvp-spec.md) เป็นรายการงานและเกณฑ์ตรวจรับก่อนใช้กับเงินและสต๊อกจริง สถานะปัจจุบันของโปรเจกต์คือ **มีสเปกและหน้าเว็บตัวอย่าง แต่ยังไม่มีระบบ production** สเปกฉบับ 0.1 ยังมีสมมติฐานที่เจ้าของร้านต้องยืนยันก่อนเริ่มพัฒนาระบบจริง

## ตอนนี้มีอะไร และยังขาดอะไร

| ส่วน | มีแล้วในโปรเจกต์ | สิ่งที่ต้องมีเพื่อขายจริง |
| --- | --- | --- |
| หน้าจอ | หน้าเว็บตัวอย่าง 7 หน้าใน `mockup/` | UI ที่เชื่อม API จริง รับมือข้อผิดพลาด และทดสอบบนเครื่องร้าน |
| กติกาขาย | โมเดล JavaScript และชุดทดสอบข้อมูลตัวอย่าง | ตรวจเงิน ราคา สต๊อก สิทธิ์ และคำขอซ้ำใน API กับ SQLite transaction จริง |
| ข้อมูล | `localStorage` ของเบราว์เซอร์ | SQLite, schema/migrations, constraints, บัญชีและประวัติที่เก็บบนดิสก์เครื่องร้าน |
| การเปิดผ่าน localhost | Python HTTP server สำหรับไฟล์ mockup | local service ที่เริ่มพร้อมเครื่อง เสิร์ฟ UI/API จากเครื่องร้าน และทำงานเมื่ออินเทอร์เน็ตขาด |
| ผู้ใช้ | สลับบทบาทเพื่อทดลองหน้าจอ | setup เจ้าของร้าน, รหัสผ่าน, session และการตรวจสิทธิ์ฝั่ง server |
| Backup | สถานะจำลองและ export JSON ตัวอย่าง | SQLite snapshot ที่ตรวจได้, คิวส่ง private cloud, retention และการซ้อม restore |
| การตรวจรับ | unit tests ของโมเดลตัวอย่าง | integration/browser/fault tests กับระบบจริง, อุปกรณ์จริง และ pilot ที่กระทบยอดได้ |

**ข้อมูลใน mockup ไม่ใช่ฐานข้อมูลร้าน** การรัน `py -m http.server` ทำให้เปิดหน้าเว็บได้เท่านั้น ไม่ได้เพิ่ม API, SQLite, การยืนยันตัวตน หรือ backup จริง ผลทดสอบของ mockup ช่วยยืนยันแนวคิดและกติกาบางส่วน แต่ยังใช้แทนหลักฐาน production ไม่ได้

## ลำดับงานก่อนใช้ขายจริง

งานด้านล่างอิง milestone M1–M6 และกติกา R01–R08 ในสเปก ให้ถือว่าแต่ละระยะเสร็จเมื่อมีทั้งโค้ด หลักฐานทดสอบ และผู้รับผิดชอบตรวจผล ไม่ใช่เพียงมีหน้าจอให้กด

### M1 — ยืนยันกติกาและสภาพร้าน

- [ ] ยืนยันจำนวนเครื่อง/สาขา วิธีนับหน่วยสินค้า บาร์โค้ด รูปแบบใบเสร็จ วันทำการ และอุปกรณ์เป้าหมาย (OS, scanner, printer, ลิ้นชักเงิน)
- [ ] ยืนยันวิธีรับเงินสด เปิด–ปิดกะ เงินนำเข้า/ออก และวิธีจัดการส่วนต่างกับเจ้าของร้าน พร้อมตัวอย่างตัวเลขที่คำนวณตรงกัน
- [ ] ตัดสินใจว่าต้องคืนบางรายการ คืนหลังปิดกะ รับสินค้าเสียหาย ชั่งน้ำหนัก หรือออกเอกสารภาษีแบบเฉพาะตั้งแต่วันแรกหรือไม่ หากจำเป็นต้องเพิ่มขอบเขตก่อน pilot
- [ ] เลือกที่เก็บ backup, วิธีดูแล credentials, สื่อสำรองเมื่อ offline และวิธีขายฉุกเฉินเมื่อเครื่องหลักเสีย โดยไม่เปิดฐานข้อมูลสองชุดขายพร้อมกัน
- [ ] ปรับสเปกและประมาณการตามคำตอบจริง แล้วให้เจ้าของร้านรับรองตัวอย่างบิล เงินกะ สต๊อก และเหตุขัดข้อง

**ผ่านเมื่อ:** สมมติฐานที่กระทบยอดเงินหรือ workflow ถูกตัดสินใจแล้ว มีเครื่อง/อุปกรณ์เป้าหมาย และมีตัวอย่างผลลัพธ์สำหรับเขียน test ได้

### M2 — ฐานระบบ local, บัญชี, สินค้า และสต๊อก

- [ ] วางโครงการ production ตามสถาปัตยกรรมที่เสนอในสเปก: React/TypeScript/Vite สำหรับ UI, Fastify/TypeScript สำหรับ local API และ SQLite ผ่าน `better-sqlite3`; ตรึงเวอร์ชันที่ตรวจความเข้ากันได้บนเครื่องเป้าหมาย
- [ ] ทำ local service ที่เริ่มอัตโนมัติหลังเปิดเครื่อง เสิร์ฟไฟล์ UI กับ API จากเครื่องร้านผ่าน loopback และเปิดได้หลัง restart ขณะตัดอินเทอร์เน็ต
- [ ] ออกแบบ schema/migrations สำหรับ users, sessions, products, inventory balances/movements, shifts, sales/items/payments, voids, idempotency, audit และ backup runs พร้อม unique/check/foreign-key constraints
- [ ] สร้าง owner ครั้งแรกบนเครื่องโดยไม่มีบัญชีเริ่มต้นร่วมกัน; ใช้ password hash และ server-side session ตาม R06, จำกัดการลองล็อกอิน และตรวจสิทธิ์ทุก API ที่เปลี่ยนข้อมูล
- [ ] ทำ API สินค้าและสต๊อก: SKU/บาร์โค้ดไม่ซ้ำ, ราคาหน่วยสตางค์, ปิดจำหน่ายแทนลบ, รับเข้าและปรับยอดนับจริงพร้อมเหตุผลและ movement ใน transaction เดียว
- [ ] วางการเก็บ secret, สิทธิ์ไฟล์ฐานข้อมูล และ log ที่ไม่บันทึกรหัสผ่าน/session/cloud credential

**ผ่านเมื่อ:** ปิดอินเทอร์เน็ตแล้วเปิดเครื่องใหม่ เข้าใช้งาน จัดการสินค้า และตรวจยอดคงเหลือย้อนกลับถึง movement ได้; cashier เรียก API ของ owner โดยตรงแล้วถูกปฏิเสธ

### M3 — การขายเงินสดที่บันทึกได้ครั้งเดียว

- [ ] ให้ server คำนวณยอดจากราคาสินค้าปัจจุบันและจำนวนเต็ม ตรวจ safe integer ราคา สต๊อก กะ และสิทธิ์ตาม R01–R03 โดยไม่เชื่อยอดที่ client ส่งมา
- [ ] ใช้ UUID request key ที่เก็บข้ามการ reload; บันทึก canonical payload hash และผลคำขอไว้ในฐานข้อมูล key เดิม+payload เดิมต้องคืนบิลเดิม ส่วน payload ต่างต้อง conflict
- [ ] บันทึก sale, รายการสินค้า, payment, stock movements/balances, audit และผล idempotency ภายใน SQLite transaction เดียว; หากรายการใดล้มเหลวต้องไม่มีผลบางส่วน
- [ ] ให้ UI มีสถานะ draft → submitting → confirmed/unresolved; เมื่อ response หายต้องค้นผลด้วย key เดิมก่อนขายบิลใหม่ และเมื่อราคาเปลี่ยนต้องให้ผู้ขายยืนยันราคาใหม่อย่างชัดเจน
- [ ] เก็บ snapshot ชื่อ/SKU/ราคาขณะขายและเลขบิล UUID ถาวร; เปิดดูและพิมพ์บิลเดิมซ้ำได้โดยไม่สร้างการขายใหม่
- [ ] ทดสอบสองคำขอชนสต๊อกเดียวกัน, process หยุดก่อน/หลัง commit, response สูญหาย, ดิสก์เต็ม และการพิมพ์ล้มเหลว

**ผ่านเมื่อ:** เงิน บิล และสต๊อกตรงกันภายใต้การส่งซ้ำหรือความล้มเหลว; ผ่านกรณี A01–A07 และส่วน checkout ของ A15 ด้วย API/SQLite จริง

### M4 — กะ ยกเลิกบิล รายงาน และ audit

- [ ] เปิดได้เพียงหนึ่งกะต่อร้าน ผูกทุกการขาย/ยกเลิก/เงินนำเข้าออกกับกะ; ปิดกะเก็บยอดคาดหวัง ยอดนับจริง ส่วนต่าง ผู้ปิด และเวลาเป็น snapshot ที่แก้ไม่ได้
- [ ] ทำ void เฉพาะ owner ในกะเดิมที่ยังเปิดและยังไม่เคย void พร้อมเหตุผลและการยืนยันคืนเงิน/รับสินค้าครบ; เก็บบิลต้นฉบับและบันทึก reversal, stock movements และ audit ใน transaction เดียว
- [ ] ใส่ unique constraint ที่ sale void, idempotency key สำหรับ void/สต๊อก/เงินสด/กะ และจัดลำดับการขายพร้อมปิดกะด้วย transaction
- [ ] ทำรายงานกะและรายวันจากข้อมูล server โดยใช้เวลา UTC ที่เก็บไว้และจัดวันตาม Asia/Bangkok; ยอดยกเลิกอยู่ในวันที่ยกเลิก ส่วนรายงานกะรวมรายการในกะเดียวกันแม้คร่อมเที่ยงคืน
- [ ] ให้รายงานและใบเสร็จตรวจย้อนถึงรายการต้นทางได้; audit การแก้ราคา สต๊อก เงินสด กะ ผู้ใช้ void และ restore โดยไม่ให้ลบประวัติผ่านแอป

**ผ่านเมื่อ:** สูตรเงินสดคาดหวังและส่วนต่างตรงกับบิล/เงินสดต้นทาง กะปิดแล้วตัวเลขไม่เปลี่ยน และผ่าน A08–A10, A14, A16 บนระบบจริง

### M5 — Backup, restore และการรับมือเหตุขัดข้อง

- [ ] ทำ SQLite consistent snapshot ผ่าน backup API ตามรอบที่สเปกกำหนด (ทุก 15 นาทีและหลังปิดกะ) พร้อม manifest ของเวอร์ชัน เวลา และ checksum; วัดพื้นที่จริงเพื่อกำหนด retention 48 ชั่วโมง/30 วัน
- [ ] อัปโหลดไป private cloud ผ่าน TLS เมื่อออนไลน์ เก็บงานค้างและ retry เมื่อส่งไม่สำเร็จ แสดงเวลา snapshot ล่าสุด เวลา upload สำเร็จล่าสุด อายุจุดกู้คืน และข้อผิดพลาดจริง
- [ ] วางสำเนาบนสื่ออีกชิ้นหากต้องจำกัดการสูญเสียเมื่อดิสก์หลักเสียระหว่าง offline และทดสอบอ่านสำเนานั้นได้
- [ ] เขียน restore runbook: เข้า maintenance mode, หยุดขาย, เก็บข้อมูลเดิม, ตรวจ checksum/schema, กู้ลงตำแหน่งสะอาด, ตรวจ integrity/จำนวนบิล/ยอดเงิน, บังคับล็อกอินใหม่ และกระทบยอดรายการที่อยู่นอกจุดกู้คืน
- [ ] เขียนขั้นตอนอัปเกรดและถอยกลับที่คำนึงถึง schema/migrations; ทดสอบกับสำเนาข้อมูลก่อนเปลี่ยนรุ่นจริง
- [ ] ซ้อม WAN/cloud ล่ม ดิสก์เต็ม เครื่องดับ และเครื่องหลักเสีย โดยไม่แสดงสถานะสำเร็จปลอมและไม่ปล่อยให้เกิดข้อมูลขายบางส่วน

**ผ่านเมื่อ:** ซ้อมกู้คืนบนเครื่อง/ตำแหน่งสะอาดได้จริง วัด RPO cloud เป้าหมายไม่เกิน 30 นาทีในสภาพที่เน็ต/ปลายทางพร้อม และ RTO เป้าหมายไม่เกิน 2 ชั่วโมงเมื่อมีเครื่องทดแทนพร้อม ตามเงื่อนไขใน R07–R08

### M6 — ตรวจรับบนเครื่องร้านและเปิด pilot

- [ ] ทำ integration tests กับ SQLite จริงและ browser tests สำหรับเส้นทางขายหลัก; ทดสอบ A01–A16 ซ้ำบน production stack และเก็บผลลัพธ์ให้ตรวจย้อนหลังได้
- [ ] วัดบนอุปกรณ์เป้าหมายด้วยข้อมูลอย่างน้อย 10,000 สินค้า/100,000 บิลพร้อม backup ตามสเปก: p95 ค้นหาต่ำกว่า 300 ms และยืนยันบิลต่ำกว่า 1 วินาทีโดยไม่รวมการพิมพ์
- [ ] ทดลอง scanner และ printer จริง รวมขั้นตอน browser print ที่ OS อาจให้เลือกเครื่องพิมพ์; ตกลงข้อจำกัดเรื่องการพิมพ์อัตโนมัติกับเจ้าของร้าน
- [ ] ทดสอบ cold start หลัง restart โดยตัด WAN: เปิด UI, login, เปิดกะ, ขายเงินสด และพิมพ์ผ่านอุปกรณ์ local ได้
- [ ] ทดลองอย่างน้อยหนึ่งวันทำการด้วยข้อมูลที่ตรวจยอดได้ กระทบยอดเงินสด บิล สต๊อก และรายงาน; บันทึกและแก้ส่วนต่างหรือข้อขัดข้องก่อนตัดสินใจเปิดใช้
- [ ] เตรียมคู่มือผู้ขาย/เจ้าของร้าน ขั้นตอนปิดกะ การเช็ก backup การขายฉุกเฉิน การติดต่อผู้ดูแล การกู้คืน และการอัปเกรด พร้อมกำหนดผู้รับผิดชอบ

**ผ่านเมื่อ:** เจ้าของร้านตรวจผล pilot และหลักฐานทดสอบแล้วอนุมัติให้ใช้ขายจริง ไม่มีข้อผิดพลาดค้างที่อาจทำให้เงิน/สต๊อกผิด ข้อมูลหาย บิลซ้ำ หรือข้ามสิทธิ์ได้

## ประตูตัดสินใจก่อนใช้เป็นระบบหลัก

ให้เปิด production เฉพาะเมื่อครบทุกข้อ:

1. สเปกและอุปกรณ์เป้าหมายได้รับการยืนยัน; เรื่องคืนสินค้า เอกสารที่ร้านต้องใช้ และวิธีขายเมื่อเครื่องเสียมีคำตอบ
2. ระบบจริงผ่าน R01–R08 และ A01–A16 ด้วย API/SQLite ไม่ใช่เฉพาะการทดสอบ mockup
3. การขายซ้ำ response สูญหาย และ process/disk failure ไม่ทำให้เกิดบิล เงิน หรือสต๊อกซ้ำ/ค้างบางส่วน
4. บัญชีและสิทธิ์ป้องกันการเรียก API โดยตรง; audit ระบุผู้ทำรายการและตรวจย้อนหลังได้
5. Backup มีจุดกู้คืนที่ตรวจได้ และมีผลซ้อม restore/กระทบยอดบนเครื่องสำรองตามเป้าหมาย RPO/RTO
6. เปิดระบบแบบตัด WAN บนเครื่องร้านได้ ทดสอบ scanner/printer และผ่านเป้าหมายประสิทธิภาพ
7. Pilot อย่างน้อยหนึ่งวันกระทบยอดได้ เจ้าของร้านมี runbook และลงชื่อยอมรับก่อนเปลี่ยนเป็นระบบขายหลัก

## หลังเปิดใช้จริง

ต้องติดตามยอดขาย/กะ ส่วนต่างสต๊อก อายุ backup งาน upload ค้าง พื้นที่ดิสก์ และ error log ทุกวัน กำหนดรอบทดสอบ restore และขั้นตอนอัปเกรดที่มีสำเนาข้อมูลก่อนเสมอ งานเช่นหลายเครื่อง โปรโมชัน สมาชิก บัตร/QR สินค้าชั่งน้ำหนัก หรือคืนบางรายการเป็น **ขอบเขตรุ่นถัดไป** ตามสเปก เว้นแต่ M1 พบว่าร้านจำเป็นต้องใช้ตั้งแต่วันแรก

ช่วงประเมิน **18–31 developer-days** ในสเปกเป็นประมาณการเบื้องต้นสำหรับนักพัฒนาหนึ่งคนก่อนยืนยันร้าน อุปกรณ์ และบริการ cloud ไม่ใช่วันส่งมอบที่รับประกัน ให้ปรับหลัง M1 และหลังแต่ละ milestone พร้อมแยกเวลารออุปกรณ์/การตัดสินใจออกจากเวลาพัฒนา
