# POS โมดูล 6 — สมาชิกและแต้มสะสม

วันที่: 21 ตุลาคม 2026 · ฉบับ 0.1 · สถานะ: สเปกสำหรับทบทวนก่อนแตกงานพัฒนา

เอกสารนี้ขยาย [POS MVP](pos-mvp-spec.md) ให้ผูกบิลกับสมาชิก สะสมแต้มจากยอดที่จ่ายจริง และใช้แต้มเป็นส่วนลดเงินสดที่ต้องจ่าย โมดูลนี้ต้องเชื่อม [คืนสินค้า/คืนเงิน](pos-returns-refunds-spec.md), [รายงานกำไรขั้นต้น](pos-gross-profit-spec.md) และ [ออเดอร์จองสินค้า](pos-orders-reservations-spec.md) ในแอปและฐานข้อมูลเดียวกัน

## 1. เป้าหมายและขอบเขต

ร้านต้องค้นสมาชิกได้โดยไม่ทำให้ checkout ช้า ผูกสมาชิกก่อนยืนยันบิล ให้แต้มครั้งเดียวเมื่อขายสำเร็จ และใช้แต้มที่มีอยู่ลดราคาบิลได้ การคืนสินค้าหรือ void ต้องคืนแต้มที่ใช้และกลับแต้มที่ได้ตามสัดส่วนอย่างตรวจสอบได้

รุ่นแรกใช้ **กติกาคงที่** เพื่อให้คำนวณได้แน่นอน:

- จ่ายเงินจริง **1 บาท ได้ 1 แต้ม** โดยปัดเศษลงจากยอดชำระเงินสดสุทธิ: `earned_points = floor(net_cash_cents / 100)`
- **1 แต้ม = ส่วนลด 1 สตางค์** ดังนั้น 100 แต้มลด 1 บาท แต้มที่ใช้เป็นจำนวนเต็มและลดได้ไม่เกินยอดสินค้าก่อนส่วนลด
- ไม่ใช้แต้มที่เพิ่งจะได้จากบิลเดียวกัน ไม่ให้แต้มจากออเดอร์ที่ยังไม่ชำระ ไม่มีวันหมดอายุของแต้มในรุ่นแรก

อัตรานี้เป็น **ข้อเสนอเพื่อทบทวน** ไม่ใช่เงื่อนไขธุรกิจที่เจ้าของยืนยันแล้ว หากต้องการอัตราอื่น ต้องแก้ policy ก่อนพัฒนา พร้อมออกแบบ version ของกติกาให้บิลเก่าไม่เปลี่ยน

**ไม่รวม:** ระดับสมาชิก, คูปอง/โปรโมชันอื่น, วันหมดอายุแต้ม, แลกของรางวัล, เติมเงินกระเป๋า, SMS/อีเมล, สมัครออนไลน์, ใช้แต้มข้ามสาขา, ซื้อเชื่อ และรายงานภาษีหรือการตีมูลค่าหนี้สินแต้มทางบัญชี

## 2. สมาชิกและข้อมูลส่วนบุคคล

สมัครสมาชิกด้วยชื่อที่ใช้เรียกและเบอร์โทรศัพท์สำหรับค้นหา/แยกบัญชี เบอร์เก็บเป็นข้อความเพื่อรักษาศูนย์นำหน้าและ normalize รูปแบบก่อนตรวจ unique; เก็บ `member_id` ถาวร ไม่ใช้เบอร์เป็น FK เมื่อเปลี่ยนเบอร์ สมาชิกต้องยินยอมให้ร้านเก็บข้อมูลเพื่อสะสมแต้ม; ออกแบบหน้าจอให้เก็บเท่าที่จำเป็น ไม่พิมพ์เบอร์เต็มบนใบเสร็จหรือ log ทั่วไป

`cashier` ค้นด้วยเบอร์ที่ลูกค้าแจ้งและเห็นข้อมูลจำเป็นสำหรับยืนยันตัวตน/แต้ม; `owner` สร้าง/แก้/ปิดใช้งานสมาชิกและดูประวัติเต็ม สมาชิกที่มีบิลหรือ ledger แล้วไม่ลบแถวทางกายภาพผ่านแอป การรวมสมาชิกซ้ำและการจัดการคำขอข้อมูลส่วนบุคคลต้องมี workflow เพิ่มก่อนใช้งานจริงหากร้านต้องรองรับ

## 3. ขั้นตอนขายและใช้แต้ม

1. ก่อนรับเงิน พนักงานเลือกสมาชิกหรือขายแบบไม่เป็นสมาชิก ระบบอ่านยอดแต้มที่ใช้ได้ ณ เวลานั้นและแสดงอัตราแต้ม/ส่วนลด
2. หากใช้แต้ม กรอกจำนวนเต็มไม่เกินยอดแต้มที่ใช้ได้และไม่เกินยอดสินค้าหน่วยสตางค์ UI แสดง **ยอดสินค้าก่อนลด, แต้มที่ใช้, ส่วนลด, ยอดเงินสดที่ต้องรับ, แต้มที่จะได้** ให้ลูกค้าตรวจ
3. ตอนยืนยันบิล API ตรวจ session, สมาชิก, ยอดแต้ม, ราคาและสต๊อกใหม่ใน transaction เดียวกับ checkout; ทำ sale/stock/payment/loyalty ledger/idempotency พร้อมกัน บิลไม่มีสมาชิกใช้แต้มไม่ได้และไม่สะสมแต้ม
4. บิลและใบเสร็จเก็บ member id, policy version, ยอดก่อนลด, ส่วนลดแต้ม, ยอดเงินสดรับสุทธิ, แต้มที่ใช้/ได้ และการจัดสรรส่วนลดตามรายการสินค้า การพิมพ์ซ้ำไม่เพิ่มแต้ม
5. เมื่อคืนบางรายการ ระบบคำนวณ refund จาก **ยอดสุทธิของหน่วยที่คืนหลังจัดสรรส่วนลด** ไม่ใช้ราคาเต็มเดิม คืนแต้มที่เคยใช้กับหน่วยนั้นและกลับแต้มที่ได้ตามยอดที่ยังคงซื้อ
6. เมื่อ void ทั้งบิล คืนแต้มที่ใช้ทั้งหมด กลับแต้มที่ได้ทั้งหมด และคืนเงินสดเท่ายอดบิลที่ลูกค้าจ่ายจริง

สามารถใช้แต้มลดเต็มยอดจนเงินสดที่ต้องรับเป็น 0 สตางค์ได้ แต่ยังต้องสร้างบิลในกะที่เปิดและบันทึกการใช้แต้ม โดยไม่เพิ่มเงินสดในลิ้นชัก บิลที่ขายก่อนเปิดโมดูลนี้ไม่ให้แต้มย้อนหลัง

การให้แต้มและคืนแต้มเมื่อ refund เป็นเรื่องที่ระบบ POS/loyalty เชิงพาณิชย์ต้องเชื่อมกันด้วย เช่น [Square Loyalty refund behavior](https://squareup.com/help/us/en/article/6130-manage-your-square-loyalty-program) กติกาตัวเลขในเอกสารนี้เป็นของระบบร้านนี้เอง

## 4. การจัดสรรส่วนลดและคืนบางรายการ

เพราะส่วนลดอยู่ระดับบิล แต่ลูกค้าอาจคืนเพียงหนึ่งหน่วย ต้องบันทึกส่วนลด **ต่อหน่วยที่ขาย** เป็นจำนวนเต็มสตางค์:

1. กระจายส่วนลดแต้มตามสัดส่วนยอดเต็มของแต่ละ sale line โดยใช้เศษส่วนจำนวนเต็ม; ปัดลง แล้วแจกสตางค์ที่เหลือตามเศษมากสุด ผูกลำดับกรณีเศษเท่ากันด้วย `sale_line_id`
2. ภายใน sale line กระจายจำนวนสตางค์ให้แต่ละหน่วยอย่างแน่นอนตาม `unit_ordinal` บันทึกผลหลัง commit และตรวจ `Σ unit_discount_cents = redeemed_points = sale_discount_cents`
3. เมื่อคืน `quantity` หน่วยจาก line เดิม ให้เลือก ordinal ที่ยังไม่คืนตามลำดับต่ำสุดแบบคงที่ `refund_cash = Σ (unit_price_cents − unit_discount_cents)` และคืนแต้มที่เคยใช้เท่ากับ `Σ unit_discount_cents` ของหน่วยที่คืน
4. แต้มที่ได้จากบิลเมื่อขาย = `floor(net_cash_cents / 100)`; หลังคืนแต่ละครั้ง target แต้มที่ควรได้ = `floor(retained_cash_cents / 100)` ระบบลง ledger กลับแต้มจำนวน `previous_earned_net − target` เพื่อให้คืนหลายครั้งแล้วรวมตรงกับคืนครั้งเดียว
5. หน่วยที่คืนแล้วคืนซ้ำไม่ได้ตาม invariant ของโมดูล 1; เงิน/แต้ม/ส่วนลดและ cost reversal ในโมดูล 4 ต้องอ้าง `return_line_id` เดียวกัน

กติกานี้ **ขยาย RT04** ในสเปกคืนสินค้า: บิลที่ไม่มีส่วนลดใช้ราคาเต็มเดิม; บิลที่ใช้แต้มคืนเงินตามยอดสุทธิของหน่วยที่คืน หลังหักส่วนลดที่ snapshot ไว้ ห้ามคืนเงินเต็มราคาแล้วคืนแต้มที่ใช้ด้วย เพราะจะให้มูลค่าซ้ำ

## 5. กติกาธุรกิจและ invariants

| รหัส | กติกา |
| --- | --- |
| LO01 | แต้มเป็น integer เก็บใน ledger แบบ append-only; balance เป็นผลรวม ledger ไม่แก้ยอดคงเหลือตรง ๆ |
| LO02 | ตอน redeem ต้องตรวจยอดแต้มก่อน sale ใน write transaction; ไม่ใช้แต้มที่เกิดจาก sale เดียวกันหรือแต้มของสมาชิกอื่น |
| LO03 | `sale_discount_cents = redeemed_points` และ `cash_due_cents = gross_cents − sale_discount_cents ≥ 0`; เงินสดที่รับหลังทอนเท่ากับ `cash_due_cents` |
| LO04 | sale, discount allocations, cash payment, stock movement, points redeem, points earn, audit และผล idempotency commit/rollback พร้อมกัน |
| LO05 | refund/void สร้าง ledger reversal ที่อ้างเหตุการณ์เดิมและ unique ต่อ source/type; คำขอซ้ำหรือ return ซ้ำไม่คืนเงินหรือแต้มซ้ำ |
| LO06 | หากแต้มที่เคยได้ถูกใช้ในบิลอื่นแล้ว ก่อนการคืนสินค้าบิลเดิม ยอดแต้มอาจติดลบหลัง reversal ได้ ให้แสดงแต้มค้างคืนและห้าม redeem ใหม่จน balance พอ; ห้ามปฏิเสธการคืนเงินลูกค้าเพราะแต้มไม่พอ |
| LO07 | รายได้ขาย รายงานกะ และเงินสดคาดหวังใช้ยอดเงินสดสุทธิหลังส่วนลด; ส่วนลดแต้มไม่ใช่ `cash out` และไม่ถูกหักซ้ำ |
| LO08 | ส่วนลดที่จัดสรรต่อหน่วยรวมเท่ายอดส่วนลดบิลทุกสตางค์และไม่เกินราคาหน่วย; refund ต่อหน่วยไม่ติดลบ |
| LO09 | ราคาขาย/ต้นทุน/กติกาแต้มที่เปลี่ยนในอนาคตไม่แก้ snapshot sale และ ledger เก่า; รายงานกำไรโมดูล 4 ใช้รายได้สุทธิหลังส่วนลด |
| LO10 | ออเดอร์จองของโมดูล 5 ยังไม่ให้แต้ม; ถ้า checkout ออเดอร์พร้อมสมาชิก ให้แต้ม/ใช้แต้มใน transaction ขายตอนรับของเท่านั้น |

## 6. โมเดลข้อมูลและ API ที่เสนอ

| ตาราง/ส่วน | ฟิลด์สำคัญ | ข้อบังคับ |
| --- | --- | --- |
| `members` | `id`, `member_no`, `name`, `phone_normalized`, `status`, `created_at` | เลขสมาชิก/เบอร์ที่ normalize ไม่ซ้ำ; ปิดใช้งานแทนลบ |
| `loyalty_policy_versions` | `id`, `earn_base_cents`, `earn_points`, `redeem_cents_per_point`, `effective_at` | sale อ้าง policy version ที่ใช้จริง; รุ่นแรกค่าคงที่ตามข้อ 1 |
| `loyalty_entries` | `id`, `member_id`, `source_type`, `source_id`, `kind`, `points_delta`, `created_at_utc` | append-only; unique `(source_type, source_id, kind)` ภายใต้ชนิดเหตุการณ์ที่หนึ่ง source สร้างหนึ่ง entry |
| `sale_unit_discounts` | `sale_line_id`, `unit_ordinal`, `discount_cents`, `returned_by_return_line_id` nullable | `UNIQUE(sale_line_id, unit_ordinal)`; ส่วนลดไม่เกินราคาหน่วย; returned ได้ครั้งเดียว |
| `sales` | เพิ่ม `member_id`, `loyalty_policy_version_id`, `gross_cents`, `points_discount_cents`, `cash_due_cents`, `points_earned` | snapshot immutable; `gross − discount = cash_due` |
| `returns` / `voids` | อ้างหน่วยที่คืนและ ledger reversal | เงินคืน/แต้มคืนคำนวณใน transaction เดียวกับ return/void |

`loyalty_entries` มี kind `EARN`, `REDEEM`, `EARN_REVERSAL`, `REDEEM_RESTORE` โดย delta เป็นบวก/ลบตามเหตุการณ์ การคืนหลายครั้งใช้ source เป็น return id ของแต่ละครั้งจึงไม่ชน unique เดิม ส่วน balance cache ถ้ามีต้องอัปเดตใน transaction เดียวและตรวจย้อนกับ ledger ได้

API ตัวอย่าง: `POST/GET /api/members`, `GET /api/members/{id}/points`, `GET /api/members/{id}/history`, checkout เดิมเพิ่ม `memberId/redeemPoints`, return/void เดิมเพิ่ม point reversals อัตโนมัติ และ `GET /api/reports/loyalty` สำหรับ owner บทบาทและข้อมูลส่วนบุคคลต้องตรวจที่ API

ข้อผิดพลาดหลัก: `MEMBER_NOT_FOUND`, `MEMBER_INACTIVE`, `INSUFFICIENT_POINTS`, `INVALID_REDEMPTION`, `LOYALTY_POLICY_CHANGED`, `IDEMPOTENCY_CONFLICT` และข้อผิดพลาดธุรกรรม POS เดิม

## 7. ตัวอย่างและรายงาน

ลูกค้าซื้อสินค้าชนิดเดียว 2 ชิ้น ชิ้นละ 35 บาท ยอดเต็ม 70 บาท ใช้ 100 แต้มลด 1 บาท: จ่ายเงินสด 69 บาท ได้ `floor(69)=69` แต้ม ระบบจัดส่วนลด 50 สตางค์ต่อชิ้น

คืน 1 ชิ้น: คืนเงินสด `35.00−0.50=34.50` บาท, คืนแต้มที่ใช้ 50 แต้ม และปรับแต้มที่ได้จาก 69 เหลือ `floor(34.50)=34` แต้ม จึงกลับแต้มที่ได้ 35 แต้ม ถ้าคืนชิ้นที่สองภายหลัง: คืนอีก 34.50 บาท คืนแต้มที่ใช้อีก 50 และกลับแต้มที่ได้อีก 34 รวมสองครั้งคืนเงิน 69 บาท คืนแต้มที่ใช้ 100 และกลับแต้มที่ได้ 69 พอดี

รายงาน owner แสดงสมาชิก active, ยอดแต้มคงเหลือ, แต้มได้/ใช้/กลับ, มูลค่าส่วนลดแต้ม, ยอดขายสมาชิกและกรณียอดแต้มติดลบ แยกจากรายงานเงินสดและกำไร ไม่เรียกยอดแต้มคงเหลือว่าเงินสดหรือกำไร

## 8. ลำดับส่งมอบและเกณฑ์ตรวจรับ

1. เจ้าของยืนยันอัตราแต้ม การระบุตัวสมาชิก และวิธีจัดการสมาชิกซ้ำ/ข้อมูลส่วนบุคคล ก่อนเขียนโค้ด
2. ขยาย sale/return/void และรายงานให้รองรับยอดสุทธิ/discount allocations พร้อม migration ของบิลเก่าเป็น `discount=0` โดยไม่แก้ยอดเดิม
3. ทำ member/loyalty ledger, API และ UI บน production SQLite พร้อม transaction, idempotency และ role checks; เชื่อม checkout ออเดอร์ในโมดูล 5
4. ทดสอบ partial refund หลายครั้ง, void, แต้มติดลบ, การแย่งใช้แต้มพร้อมกัน, response หาย, restore และรายงานเงินกะ/กำไร

| กรณีตรวจรับ | ผลที่ต้องได้ |
| --- | --- |
| ขาย 70 บาท ใช้ 100 แต้ม | ส่วนลด 1 บาท เงินสดเข้ากะ 69 บาท ได้ 69 แต้ม; ส่วนลดรวมต่อหน่วย 100 สตางค์ |
| คืน 1 จาก 2 ชิ้นตามตัวอย่าง | เงินคืน 34.50 บาท คืน 50 แต้มที่ใช้ และกลับ 35 แต้มที่ได้ |
| คืนชิ้นที่สอง | เงินคืนสะสม 69 บาท แต้มใช้คืนครบ 100 แต้ม แต้มได้กลับครบ 69 |
| void บิลที่ใช้แต้ม | คืนเงินที่จ่ายจริง กลับแต้มได้ และคืนแต้มใช้ทั้งหมดเพียงครั้งเดียว |
| แลกแต้มสองบิลพร้อมกันจาก balance เดียว | สำเร็จตามยอดที่มีได้ไม่เกินหนึ่งชุด; อีกคำขอแต้มไม่พอ |
| คืนสินค้าหลังใช้แต้มที่เคยได้ไปแล้ว | คืนเงินได้; balance แต้มอาจติดลบและ redeem เพิ่มไม่ได้จนชดเชย |
| checkout หรือ return response หาย | key เดิมได้ผลเดิม ไม่มีแต้ม/เงิน/stock ซ้ำ |
| cashier เรียก member history เต็มหรือแก้ policy | ถูกปฏิเสธตามสิทธิ์; ข้อมูลติดต่อไม่หลุดใน log/ใบเสร็จ |

**เกณฑ์พร้อมใช้จริง:** เงินกะตรงยอดหลังส่วนลด, refund บางหน่วยไม่คืนมูลค่าซ้ำ, ledger แต้มตรวจกลับถึงบิล/return ได้, รายงานกำไรใช้ยอดสุทธิ, และธุรกรรมชนกัน/ส่งซ้ำผ่านการทดสอบกับ SQLite จริง
