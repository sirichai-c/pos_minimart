# POS โมดูล 4 — รายงานกำไรขั้นต้น

วันที่: 21 ตุลาคม 2026 · ฉบับ 0.1 · สถานะ: สเปกสำหรับทบทวนก่อนแตกงานพัฒนา

เอกสารนี้ต่อจาก [POS MVP](pos-mvp-spec.md), [โมดูลจัดซื้อและรับสินค้า](pos-purchasing-receiving-spec.md), [โมดูลตรวจนับสต๊อก](pos-stock-count-spec.md) และ [โมดูลคืนสินค้า](pos-returns-refunds-spec.md) ใช้รายได้จากบิลขายและต้นทุนของสินค้าที่ขายจริงเพื่อรายงานกำไรขั้นต้นแยกสินค้า/วัน/กะ ไม่ใช่ระบบบัญชีหรือรายงานกำไรสุทธิ

## 1. เป้าหมายและเงื่อนไขความถูกต้อง

เจ้าของร้านต้องเห็น `รายได้สุทธิ − ต้นทุนสินค้าที่ขาย = กำไรขั้นต้น` พร้อมเจาะถึงบิลและที่มาของต้นทุนได้ ราคาทุนที่บันทึกตอนรับของในโมดูล 2 เป็นแหล่งข้อมูลสำคัญ แต่ต้องกำหนดด้วยว่าสต๊อกตั้งต้น การรับเข้าแบบ manual การปรับยอด และการคืนสินค้าใช้ต้นทุนใดก่อนคำนวณรายงาน

รายงานต้องแยก **ต้นทุนที่ทราบ** กับ **ต้นทุนที่ไม่ทราบ** ชัดเจน ห้ามตีต้นทุนที่ไม่ทราบเป็นศูนย์แล้วแสดงกำไรสูงเกินจริง สูตรกำไรขั้นต้นทั่วไปคือยอดขายสุทธิลบต้นทุนสินค้าที่ขาย และความแม่นยำขึ้นกับการมีข้อมูลต้นทุนตาม [Shopify analytics fields](https://help.shopify.com/en/manual/reports-and-analytics/shopify-reports/report-types/analytics-fields)

**ไม่รวม:** ค่าเช่า ค่าแรง ค่าน้ำไฟ ภาษี ค่าขนส่ง/ส่วนลดซื้อที่ต้องกระจายต้นทุน บัญชีเจ้าหนี้ สินค้าล็อต/หมดอายุ หลายสาขา และกำไรสุทธิ นโยบายนี้เป็นตัวเลขเพื่อบริหารร้าน ไม่ใช่การรับรองมาตรฐานบัญชีหรือภาษี

## 2. วิธีคิดต้นทุนที่เลือก

เลือก **FIFO ต่อสินค้า** สำหรับสินค้าจำนวนเต็ม: สินค้าเข้าแต่ละครั้งสร้าง cost layer ตามลำดับเวลา ขายแล้วใช้ต้นทุนจาก layer เก่าก่อน บันทึก allocation ของต้นทุนบน sale line ขณะ checkout โดยไม่คำนวณย้อนหลังจากราคาทุนปัจจุบัน วิธีนี้รองรับต้นทุนรับของแต่ละรอบที่ไม่เท่ากันและทำให้บิลเก่ายังมีต้นทุนเดิม

ทางเลือกที่ง่ายกว่าคือใช้ “ราคาทุนล่าสุด × จำนวนขาย” แต่จะทำให้กำไรบิลเดิมเปลี่ยนเมื่อรับของใหม่ จึงไม่เลือกในโมดูลนี้ วิธีเฉลี่ยถ่วงน้ำหนักทำได้แต่ต้องออกแบบการปัดเศษของเศษสตางค์ทุกธุรกรรมเพิ่ม FIFO ที่ต้นทุนต่อหน่วยเป็นจำนวนเต็มสตางค์ตรวจกลับถึงใบรับได้ง่ายกว่า

| เหตุการณ์ | ผลต่อ cost layers |
| --- | --- |
| รับของดีตามใบรับ PO | สร้าง layer `accepted_qty` ที่ `actual_unit_cost_cents`; ของปฏิเสธไม่สร้าง layer |
| สต๊อกตั้งต้นหรือรับเข้า manual | สร้าง layer พร้อมต้นทุนที่ owner ระบุ; ถ้าไม่ทราบ ให้เก็บ `cost_unknown` อย่างชัดเจน |
| ขาย | ใช้ layer เก่าตาม FIFO ตามจำนวนขาย; บันทึก allocation/ต้นทุนลง sale line แบบ immutable |
| void ทั้งบิล | กลับต้นทุนขายของบิลที่ void ในวันที่ void และสร้าง layer ใหม่ของสินค้าที่กลับเข้าสต๊อก โดยใช้ต้นทุนเดิม |
| คืนสินค้าจากลูกค้า | กลับต้นทุนขายของจำนวนที่คืนในวันที่คืน; ส่วนขายต่อได้สร้าง layer ที่ต้นทุนเดิม; ส่วนเสียหายไม่เพิ่มสต๊อกและบันทึกต้นทุนเสียหายแยก |
| ตรวจนับ/ปรับยอดลบ | ใช้ layer ออกตาม FIFO และบันทึกมูลค่าคลาดเคลื่อนแยกจาก COGS ของการขาย |
| ตรวจนับ/ปรับยอดบวก | สร้าง layer ที่ต้นทุนซึ่ง owner ระบุ หรือ `cost_unknown`; ไม่เดาเป็นราคาทุนล่าสุด |

`cost_unknown` เป็นค่าไม่มีข้อมูล ไม่ใช่ต้นทุน 0 บาท ส่วนราคาทุน 0 บาทที่เจ้าของยืนยัน เช่น ของแถม เป็นข้อมูลต้นทุนที่ทราบได้

## 3. กติกาธุรกิจและ invariants

| รหัส | กติกา |
| --- | --- |
| GP01 | หน่วยเงินทั้งหมดเป็น integer สตางค์ ต้นทุนต่อหน่วยของ layer เป็นจำนวนเต็มตั้งแต่ 0 หรือ `unknown`; ตรวจ safe integer ของผลรวม |
| GP02 | ทุกการขาย consume cost layers ตาม FIFO ใน transaction เดียวกับ sale/stock movement; `Σ allocated_qty = sold_qty` และ `Σ layer.remaining_qty = on_hand_qty` ต่อ SKU หลังธุรกรรม |
| GP03 | บิลขายเก็บ sale price snapshot ตาม POS เดิม และ cost allocation snapshot ที่แก้ย้อนหลังไม่ได้ การเปลี่ยนราคาขายหรือต้นทุนสินค้าใหม่ไม่แก้บิลเก่า |
| GP04 | การรับสินค้า, การขาย, void, return และ stock adjustment ทุกทางที่เปลี่ยน `on_hand` ต้องอัปเดต cost layers ใน transaction เดียว; ห้ามมี movement ที่ทำให้ layer quantity กับ balance ไม่ตรง |
| GP05 | Return/void กลับ COGS โดยอ้าง allocation ของบิลเดิม จำนวนคืนสะสมต่อ allocation ไม่เกินจำนวนที่ขาย; การเลือกหน่วยที่คืนจากหลาย allocation ใช้ลำดับที่กำหนดตายตัว (allocation ล่าสุดก่อน) และเก็บผลไว้ |
| GP06 | Return เสียหายกลับ COGS ของการขายเช่นเดียวกับคืนดี แล้วบันทึก `damage_writeoff_cost` แยก สต๊อกไม่เพิ่ม จึงไม่ซ่อนต้นทุนเสียหายในกำไรขั้นต้น |
| GP07 | รายงานช่วงที่มีต้นทุนไม่ทราบต้องแสดง `cost coverage` และสถานะ `กำไรขั้นต้นยังคำนวณครบไม่ได้`; ไม่รวมรายการไม่ทราบเป็นต้นทุน 0 ในยอดกำไรที่อ้างว่าเต็มช่วง |
| GP08 | เหตุการณ์รายได้และต้นทุนที่กลับรายการอยู่ในวันที่/กะของเหตุการณ์นั้น กะเดิมที่ปิดแล้วไม่เปลี่ยน snapshot และรายงานไม่ย้าย return ไปวันขายเก่า |
| GP09 | รายงานดูได้เฉพาะ owner; cashier ไม่เห็นราคาทุนหรือกำไรผ่าน UI หรือ API |
| GP10 | เมื่อโมดูล 6 ใช้แต้มเป็นส่วนลด ให้รายได้ของ sale line เป็นยอดสุทธิหลังจัดสรรส่วนลดที่ snapshot ไว้ ต้นทุน FIFO ไม่เปลี่ยน |

## 4. การเริ่มใช้กับข้อมูลเดิม

ก่อนเปิดรายงานกำไร ให้บันทึก `activation_at` และสร้าง opening cost layers จาก stock balance ปัจจุบันของทุกสินค้า owner ใส่ต้นทุนตั้งต้นที่ทราบได้ หากไม่ทราบจริงให้สร้าง unknown layer แล้วแสดงความไม่ครบของรายงาน การเริ่มใช้ไม่ย้อนสร้างต้นทุนที่พิสูจน์ไม่ได้ให้กับยอดขายก่อนวันเปิดโมดูล

เมื่อร้านใช้ระบบ POS ขายไปแล้วก่อนเปิดโมดูลนี้:

- บิลเก่าอาจไม่มีข้อมูลต้นทุนเพียงพอ ให้แสดงยอดขายเดิมได้ แต่ไม่แสดงกำไรขั้นต้นเต็มช่วงสำหรับบิลเหล่านั้น
- ตั้งแต่เปิดโมดูลใหม่ ทุกการขายต้อง snapshot cost allocation หรือ `unknown` แม้สินค้ายังไม่ทราบต้นทุน ห้ามบล็อกการขายจริงเพียงเพราะข้อมูลกำไรไม่ครบ
- การเพิ่มต้นทุนให้สินค้าในอนาคตไม่แก้ allocation ของบิลที่ขายไปแล้ว หากต้องปรับข้อมูลย้อนหลังต้องออก workflow แก้ไขพร้อม audit แยกในรุ่นถัดไป

## 5. โมเดลข้อมูลและ API ที่เสนอ

| ตาราง/ส่วน | ฟิลด์สำคัญ | ข้อบังคับ |
| --- | --- | --- |
| `inventory_cost_layers` | `id`, `product_id`, `source_movement_id`, `original_qty`, `remaining_qty`, `unit_cost_cents` nullable, `created_at_utc` | FK ไป movement; `0 ≤ remaining ≤ original`; ลำดับ FIFO แน่นอน |
| `sale_cost_allocations` | `id`, `sale_line_id`, `cost_layer_id`, `quantity`, `unit_cost_cents` nullable | ผลรวม quantity เท่า sale line quantity; ไม่แก้หลัง commit |
| `cost_reversals` | `id`, `source_allocation_id`, `return_line_id` หรือ `void_id`, `quantity`, `amount_cents` nullable, `created_at_utc` | จำนวนกลับรวมไม่เกิน allocation เดิม; event ไม่ซ้ำ |
| `cost_writeoffs` | `id`, `source_event_id`, `kind`, `quantity`, `amount_cents` nullable | เก็บของเสียหาย/ส่วนต่างนับแยกจาก COGS |
| `gross_profit_activation` | `activation_at`, `activated_by`, `policy_version` | ระบุขอบเขตช่วงที่ข้อมูลต้นทุนเริ่มครบ/ไม่ครบ |

ถ้าหนึ่ง allocation มีต้นทุน unknown ผลรวม COGS/กำไรของกลุ่มนั้นถือว่า incomplete แม้ส่วนอื่นมีต้นทุน การใช้ `NULL` ในรายงานต้องแยกจากศูนย์อย่างชัดเจน API `GET /api/reports/gross-profit?from=&to=&groupBy=product|day|shift` และ `GET /api/reports/gross-profit/sales/{saleId}` ให้ owner drill down ถึง sale line, cost allocation, receipt/stock movement และ reversal ส่วนการตั้งต้นใช้ owner-only API พร้อม request key/audit

## 6. สูตรรายงานและตัวอย่าง

```text
รายได้สุทธิช่วงเวลา = ยอดขายก่อนส่วนลดในช่วง − void สุทธิในช่วง − refund สุทธิในช่วง − ส่วนลดจากแต้มของยอดขายในช่วง
COGS สุทธิช่วงเวลา = ต้นทุนสินค้าที่ขายในช่วง − ต้นทุนที่กลับจาก void/return ในช่วง
กำไรขั้นต้น = รายได้สุทธิช่วงเวลา − COGS สุทธิช่วงเวลา
อัตรากำไรขั้นต้น = กำไรขั้นต้น ÷ รายได้สุทธิ (แสดงเฉพาะเมื่อรายได้สุทธิ > 0 และต้นทุนครบ)
```

หมายเหตุ: ส่วนลดจากแต้มในโมดูล 6 ต้องหักจากรายได้ขาย **ครั้งเดียว** หากยอดขายที่ดึงมาเป็นยอดหลังส่วนลดแล้ว อย่าหักซ้ำ

ตัวอย่าง FIFO: เปิดต้น 2 ชิ้นต้นทุน 20 บาท รับเพิ่ม 3 ชิ้นต้นทุน 25 บาท ขาย 4 ชิ้นราคา 40 บาท: รายได้ 160 บาท, COGS `(2×20)+(2×25)=90` บาท, กำไรขั้นต้น 70 บาท, คงเหลือ 1 ชิ้นต้นทุน 25 บาท ต่อมาคืน 1 ชิ้นราคา 40 บาทจาก allocation ล่าสุดต้นทุน 25 บาท: วันที่คืนมีรายได้ `−40` บาท, COGS `−25` บาท, ผลต่อกำไรขั้นต้น `−15` บาท; ถ้าสินค้าคืนเสียหาย ให้บันทึก write-off 25 บาทแยกและไม่เพิ่มสต๊อก

รายงานแสดงจำนวนบรรทัดขายทั้งหมด จำนวน/มูลค่าที่มีต้นทุนครบ จำนวน unknown และ `coverage = quantity_with_known_cost ÷ sold_quantity` หาก coverage ต่ำกว่า 100% ให้แสดง “กำไรที่คำนวณได้เฉพาะข้อมูลที่มีต้นทุน” จากรายได้และ COGS ของหน่วยที่รู้ต้นทุนเท่านั้นเป็นตัวเลขแยก และไม่แสดงค่าเป็นกำไรทั้งหมดของร้าน

## 7. ลำดับส่งมอบและเกณฑ์ตรวจรับ

1. ยืนยันวิธี FIFO และต้นทุนเปิดต้นของสินค้าในร้าน; ระบุวันที่เริ่มนับกำไร
2. ทำ migration/cost layers ใน production SQLite และเชื่อมทุกเส้นทางเปลี่ยนสต๊อกก่อนเปิดรายงาน ใช้ transaction เดิมของ sale/return/receipt/count
3. ทำรายงาน owner-only พร้อม drill-down และ completeness badge; ตรวจยอดกับตัวอย่างคำนวณมือ
4. ทดสอบกับข้อมูลเก่า/unknown cost, คำขอซ้ำ, concurrency, rollback, restore และคืนสินค้าข้ามวัน

| กรณีตรวจรับ | ผลที่ต้องได้ |
| --- | --- |
| FIFO ตัวอย่าง 2@20 + 3@25 ขาย 4@40 | รายได้ 160, COGS 90, กำไร 70 บาท; layer คงเหลือ 1@25 |
| เปลี่ยนราคาทุน/ราคาขายภายหลัง | รายงานบิลเดิมยังใช้ snapshot เดิม |
| คืน 1 ชิ้นจากตัวอย่าง | คืนรายได้ 40 และ COGS 25 ในวันคืน; กำไรช่วงคืน −15 บาท |
| คืนดีเทียบคืนเสียหาย | คืนดีเพิ่ม stock/cost layer; คืนเสียหายไม่เพิ่ม stock แต่มี write-off 25 บาท |
| สต๊อกตั้งต้น unknown แล้วขาย | บิลขายสำเร็จ แต่กำไรกลุ่มนั้น incomplete ไม่ถือว่าต้นทุนเป็น 0 |
| ตรวจนับลด 2 ชิ้น | layer ลดพร้อม balance; cost variance แยกจาก COGS ของการขาย |
| cashier เรียก API รายงานกำไร | ถูกปฏิเสธและไม่เห็นต้นทุน |
| transaction ล้มเหลวกลาง checkout | ไม่เกิด sale/stock movement/cost allocation บางส่วน |

**เกณฑ์พร้อมใช้จริง:** มูลค่าต้นทุนตรวจกลับถึง receipt/opening layer ได้, quantity ของ layers เท่ากับ stock balance, return/void ไม่เปลี่ยนบิลเก่า, รายงานไม่อ้างกำไรเต็มช่วงเมื่อ cost coverage ไม่ครบ และทดสอบด้วย SQLite จริง
