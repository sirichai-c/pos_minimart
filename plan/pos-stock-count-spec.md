# POS โมดูล 3 — ตรวจนับสต๊อก

วันที่: 21 ตุลาคม 2026 · ฉบับ 0.1 · สถานะ: สเปกสำหรับทบทวนก่อนแตกงานพัฒนา

เอกสารนี้ต่อจาก [สเปก POS MVP](pos-mvp-spec.md) และ [โมดูลจัดซื้อ/รับสินค้า](pos-purchasing-receiving-spec.md) โดยใช้บัญชีสินค้าและ stock movement ชุดเดียวกัน จุดประสงค์คือให้นับของจริง เปรียบเทียบยอดในระบบ และให้เจ้าของร้านอนุมัติส่วนต่างพร้อมประวัติ ไม่ใช่สร้างระบบสต๊อกอีกชุด

## 1. เป้าหมายและขอบเขต

ร้านทำรอบนับเฉพาะสินค้าบางรายการหรือทั้งร้านได้ ผู้ขายสแกน/กรอกยอดที่เห็นจริง แล้วส่งให้เจ้าของร้านตรวจและอนุมัติ สต๊อกเปลี่ยน **เฉพาะตอนอนุมัติ** พร้อม movement อ้างอิงรอบนับ และตรวจได้ว่าความต่างเกิดจากการนับครั้งใด

รุ่นแรกนับเป็นจำนวนเต็มหน่วยชิ้น หนึ่งร้าน หนึ่งคลัง/จุดขาย สินค้าที่จองให้ลูกค้าในโมดูล 5 แต่ยังอยู่ในร้านให้นับรวมเป็นของจริง สินค้าเสียหายที่แยกออกจากยอดขายได้แล้วและไม่ได้อยู่ใน stock balance ไม่ให้นับรวม

**ไม่รวม:** หลายสาขา/หลายตำแหน่งเก็บ, ล็อตหรือหมายเลขเครื่อง, เครื่องชั่ง, การนับหลายทีมพร้อมกัน, การอนุมัติหลายชั้น, ประเมินมูลค่าสินค้าสูญหายเป็นค่าใช้จ่ายทางบัญชี และการ import ไฟล์นับจากภายนอก

## 2. แนวทางที่เลือก

ใช้ **count session → นับ → ส่งตรวจ → owner อนุมัติ → movement** แทนการกดแก้ balance ทันที วิธีนี้แยกผู้พบส่วนต่างกับผู้ตัดสินใจปรับยอด และยังใช้ stock adjustment เดิมสำหรับเหตุพิเศษที่ไม่ใช่รอบนับ

ร้านยังขายระหว่างนับได้ แต่หากสินค้าใดมี stock movement หลัง snapshot ที่ใช้นับ สินค้านั้นเป็น **stale** และต้องนับใหม่ก่อนอนุมัติ ไม่เอายอดเก่ามาทับการขาย/รับของที่เพิ่งเกิด แนวทางนี้สอดคล้องกับคำแนะนำให้จัดรอบนับช่วงร้านเงียบและตรวจส่วนต่างก่อนปรับยอดใน [Shopify POS inventory counts](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/inventory-management/planning-an-inventory-count)

## 3. ขั้นตอนใช้งาน

1. `owner` เปิดรอบนับ เลือกสินค้าเป้าหมาย (บาง SKU หรือทั้งหมด รวมสินค้าปิดจำหน่ายที่ยังมีคงเหลือ) และระบุชื่อ/พื้นที่ที่นับ ระบบเก็บ `expected_qty` กับ `stock_version` ของแต่ละสินค้า ณ เวลาเริ่ม เปิดได้เพียงหนึ่งรอบต่อร้านในเวลาเดียวกัน
2. `cashier` หรือ `owner` สแกนบาร์โค้ดหรือค้น SKU แล้วกรอก **ยอดรวมที่เห็นจริง** เป็นจำนวนเต็มตั้งแต่ 0; การสแกนซ้ำอาจเพิ่มตัวนับบนหน้าจอ แต่ก่อนส่งต้องแสดงยอดสุดท้ายชัดเจน สินค้าที่ยังไม่กรอกถือว่า `uncounted` ไม่ใช่ 0
3. ส่งตรวจแล้วล็อกข้อมูลนับที่ส่ง เจ้าของร้านเห็นยอดในระบบ ณ ตอนเริ่ม ยอดที่นับ ผลต่าง และ movement ระหว่างนับ หากมีรายการ stale ให้เปิดนับใหม่เฉพาะรายการนั้นโดยเก็บประวัติค่าก่อนหน้า
4. เจ้าของร้านตรวจความผิดปกติ ระบุเหตุผลส่วนต่างอย่างน้อยเมื่อ `counted_qty != expected_qty` และอนุมัติทั้งรอบใน transaction เดียว ระบบตรวจ `stock_version` อีกครั้งก่อนสร้าง movement
5. หากรายการใด stale หรือข้อมูลไม่ครบ ให้ปฏิเสธการอนุมัติทั้งรอบจนกว่าจะนับใหม่/กรอกครบ ไม่มี balance ใดเปลี่ยนบางส่วน
6. หลังอนุมัติ เปิดดูผลรอบนับ ผู้ทำ ผู้อนุมัติ เวลา ยอดก่อน/หลัง และ movement; ยกเลิกรอบที่ยังไม่อนุมัติได้พร้อมเหตุผล รอบที่อนุมัติแล้วไม่แก้ย้อนหลัง

สำหรับการนับทั้งร้าน แนะนำทำก่อนเปิดหรือหลังปิดร้านเพื่อลดจำนวนรายการ stale; ระบบยังต้องตรวจ concurrency เสมอ

## 4. กติกาธุรกิจและ invariants

| รหัส | กติกา |
| --- | --- |
| SC01 | `owner` สร้าง/อนุมัติ/ยกเลิกรอบ; `cashier` บันทึกและส่งยอดนับได้ แต่เรียก API อนุมัติหรือแก้ balance โดยตรงไม่ได้ |
| SC02 | หนึ่งรอบมีรายการสินค้าไม่ซ้ำและอย่างน้อยหนึ่งรายการ; ขณะอนุมัติทุกรายการต้องมี `counted_qty` ที่กรอกจริง รวมค่า 0 ได้ |
| SC03 | เก็บ `expected_qty` และ `stock_version` ต่อสินค้าตอนเริ่มหรือตอนนับใหม่; ถ้า version ปัจจุบันต่างจาก snapshot ให้ stale แม้ balance บังเอิญกลับมาเท่าเดิม |
| SC04 | `delta = counted_qty − expected_qty`; เมื่ออนุมัติ version ต้องยังตรง แล้วเพิ่ม stock movement `count_adjustment` จำนวน `delta` เฉพาะรายการที่ `delta != 0` พร้อมปรับ balance ใน transaction เดียว |
| SC05 | รอบนับไม่แก้ยอดขาย, PO, ใบรับ, return หรือ reservation เดิม; movement นับเป็นเหตุการณ์ใหม่และอ้างอิง count line |
| SC06 | การอนุมัติ/ส่ง/ยกเลิกใช้ request key; key เดิม + payload เดิมได้ผลเดิม, key เดิม + payload ต่าง conflict; รอบที่อนุมัติแล้วใช้ key ใหม่อนุมัติซ้ำไม่ได้ |
| SC07 | ใบรับของ, ขาย, void, คืนสินค้า, stock adjustment และการอนุมัติรอบนับเพิ่ม `stock_version` ทุกครั้งที่กระทบสินค้า |
| SC08 | ห้ามอนุมัติแล้วทำให้ balance ติดลบ; เมื่อมี reservation ของโมดูล 5 หาก `counted_qty < active_reserved_qty` ต้องแก้ reservation/ติดต่อผู้รับจองก่อนอนุมัติ ไม่ปล่อยให้ของจองเกินของจริง |
| SC09 | รอบนับที่อนุมัติแล้วเป็น append-only; หากพบว่านับผิด ต้องสร้างรอบใหม่หรือ stock adjustment พร้อมเหตุผล ไม่ลบ movement เดิม |

วันที่เวลาที่ server บันทึกใช้ UTC; หน้าจอและรายงานแสดง `Asia/Bangkok` จำนวนส่วนต่างอาจติดลบ แต่ balance หลังอนุมัติต้องไม่ติดลบ

## 5. โมเดลข้อมูลและ API ที่เสนอ

| ตาราง/ส่วน | ฟิลด์สำคัญ | ข้อบังคับ |
| --- | --- | --- |
| `stock_counts` | `id`, `count_no`, `status`, `scope`, `created_by`, `submitted_at`, `approved_by`, `approved_at`, `reason` | เลขรอบนับไม่ซ้ำ; หนึ่งรอบ active ต่อร้าน |
| `stock_count_lines` | `id`, `count_id`, `product_id`, `expected_qty`, `stock_version`, `counted_qty`, `counted_by`, `counted_at`, `variance_reason` | `UNIQUE(count_id, product_id)`; `NULL` = ยังไม่ได้นับ, 0 = นับได้ศูนย์ |
| `stock_count_line_revisions` | `line_id`, ค่าก่อน/หลัง, ผู้แก้, เวลา, เหตุผล | เก็บการนับใหม่และแก้ค่าเมื่อ stale ตรวจย้อนหลังได้ |
| `stock_movements` | ชนิด `count_adjustment`, `reference_count_line_id` | สร้างเมื่อ delta ไม่เป็นศูนย์เท่านั้น; balance เปลี่ยนใน transaction เดียว |
| `inventory_balances` | เพิ่ม `version` ต่อสินค้า | เพิ่ม version เมื่อ movement เปลี่ยนยอด เพื่อจับ stale แม้ยอดกลับมาเดิม |

API ตัวอย่าง: `POST /api/stock-counts`, `PUT /api/stock-counts/{id}/lines/{productId}`, `POST /api/stock-counts/{id}/submit`, `POST /api/stock-counts/{id}/approve`, `POST /api/stock-counts/{id}/cancel`, `GET /api/stock-counts/{id}` ทุก endpoint ตรวจบทบาทและ state ฝั่ง API การอนุมัติใช้ SQLite write transaction ตรวจ versions/สิทธิ์/ข้อมูลครบ แล้วเขียน movements, balances, audit และ idempotency result พร้อมกัน

ข้อผิดพลาดหลัก: `COUNT_ALREADY_ACTIVE`, `COUNT_NOT_COMPLETE`, `COUNT_STALE`, `COUNT_ALREADY_APPROVED`, `RESERVATION_EXCEEDS_STOCK`, `FORBIDDEN`, `IDEMPOTENCY_CONFLICT` และข้อผิดพลาดการบันทึกเดิม

## 6. รายงานและตัวอย่าง

รายงานรอบนับแสดงจำนวน SKU ที่นับ, จำนวน SKU มีผลต่าง, ผลต่างสุทธิเป็นชิ้น, ผลต่างแยกสินค้า/เหตุผล และลิงก์ movement ตัวเลขมูลค่าเงินยังไม่แสดงจนกว่าจะมีนโยบายต้นทุนจากโมดูล 4; การมีราคาทุนบางรายการไม่ได้ทำให้ตีมูลค่าทุกส่วนต่างได้ถูกต้อง

ตัวอย่าง: ระบบมีน้ำ 10 ชิ้น เปิดรอบนับและนับได้ 8 ชิ้น เจ้าของอนุมัติเมื่อ version ยังเดิม: movement `−2`, balance เป็น 8 หากขาย 1 ชิ้นหลังนับแต่ก่อนอนุมัติ ระบบเป็น 9 ชิ้นและ version เปลี่ยน การอนุมัติต้องถูกปฏิเสธให้กลับไปนับใหม่ ไม่ตั้ง balance เป็น 8 โดยอัตโนมัติ

## 7. ลำดับส่งมอบและเกณฑ์ตรวจรับ

1. ทดลอง flow หน้านับ/ส่งตรวจ/อนุมัติใน mockup โดย migration ข้อมูลตัวอย่าง ไม่ถือว่า `localStorage` เป็น transaction จริง
2. ทำ schema/API บน production SQLite หลังฐาน stock movement ใช้งานได้ เพิ่ม version ต่อสินค้าและ migration จาก balance เดิมโดยไม่ลบประวัติ
3. ทดสอบ concurrency ระหว่างนับกับขาย/รับของ/คืนสินค้า และกรณีส่งคำขอซ้ำ, response หาย, disk failure, restore
4. ทดลองนับ SKU จริงในร้านและเทียบ movement/ยอดคงเหลือก่อนใช้ปรับสต๊อกจริง

| กรณีตรวจรับ | ผลที่ต้องได้ |
| --- | --- |
| นับ SKU หนึ่งได้ 8 จากระบบ 10 | ก่อนอนุมัติยังเป็น 10; หลังอนุมัติเป็น 8 และมี movement −2 หนึ่งรายการ |
| กรอก 0 กับไม่กรอก | 0 หมายถึงนับได้ศูนย์; ไม่กรอกทำให้ส่ง/อนุมัติไม่ได้ |
| ขายหรือรับของหลัง snapshot แม้ balance กลับค่าเดิม | version เปลี่ยน; บังคับนับ SKU นั้นใหม่ |
| ส่ง approve key เดิมซ้ำ / key ใหม่ซ้ำ | key เดิมคืนผลเดิม; key ใหม่ถูกปฏิเสธ ไม่มี movement เพิ่ม |
| cashier เรียก approve API | `FORBIDDEN`; balance ไม่เปลี่ยน |
| พบของจริงน้อยกว่าจำนวนที่จอง | อนุมัติไม่ได้จนจัดการ reservation |
| storage failure ระหว่างอนุมัติ | ไม่มี count approved หรือ movement/balance บางส่วน |

**เกณฑ์พร้อมใช้จริง:** รอบนับไม่ทับการเคลื่อนไหวระหว่างนับ, ตรวจกลับถึงผู้ทำ/ผู้อนุมัติได้, รับค่าศูนย์อย่างถูกต้อง, และทดสอบ atomicity/idempotency กับ SQLite จริงก่อนใช้กับสต๊อกร้าน
