# POS โมดูลจัดซื้อและรับสินค้าเข้าร้าน

วันที่: 21 ตุลาคม 2026 · ฉบับ 0.1 · สถานะ: สเปกสำหรับทบทวนก่อนแตกงานพัฒนา

เอกสารนี้เป็น **โมดูลลำดับ 2** ต่อจาก [โมดูลคืนสินค้าและคืนเงินสด](pos-returns-refunds-spec.md) และขยาย [สเปก POS MVP](pos-mvp-spec.md) ในส่วนจัดซื้อ/รับสินค้า ใช้แอปและฐานข้อมูลเดียวกับ POS เดิม ไม่ใช่ระบบใหม่แยกต่างหาก ปัจจุบันโครงการมี mockup ที่รับสต๊อกเข้าแบบระบุจำนวนและเหตุผล แต่ยังไม่มีใบสั่งซื้อ ซัพพลายเออร์ ใบรับของ หรือระบบ production API/SQLite

## 1. เป้าหมายและขอบเขต

เจ้าของร้านต้องสั่งสินค้าจากซัพพลายเออร์ บันทึกของที่มาถึงจริงได้หลายครั้ง และตรวจได้ว่าแต่ละใบสั่งซื้อยังค้างรับกี่ชิ้น สต๊อกเพิ่มเฉพาะสินค้าที่ตรวจรับแล้ว รายการรับทุกครั้งต้องย้อนถึงใบสั่งซื้อ ผู้รับ เวลา และเอกสารส่งของได้

**ขอบเขตรุ่นแรก:** หนึ่งร้าน, สินค้านับจำนวนเต็ม, ซัพพลายเออร์, ใบสั่งซื้อ (PO), รับของบางส่วน/หลายครั้ง, บันทึกของเสียหายที่ไม่รับเข้าสต๊อก, ราคาทุนที่ตกลงและราคาจริงตอนรับ, ประวัติและรายงานค้างรับ `owner` เป็นผู้สร้าง/ออก PO และยืนยันรับของตามสิทธิ์จัดการสต๊อกของ POS เดิม ไม่ต้องเปิดกะขายเพื่อทำงานจัดซื้อ

**ยังไม่รวม:** เจ้าหนี้การค้า, กำหนดชำระ/ชำระเงิน, ภาษีซื้อหรือเอกสารภาษี, ส่ง PO อัตโนมัติทางอีเมล, อนุมัติหลายระดับ, คืนสินค้าให้ซัพพลายเออร์, ล็อต/วันหมดอายุ, หน่วยซื้อกับหน่วยขายที่ต่างกัน, ส่วนลด/ค่าขนส่งกระจายเข้าต้นทุน, การคำนวณ COGS/กำไร และหลายสาขา ตัวเลขต้นทุนในโมดูลนี้ใช้ตรวจการซื้อ ไม่ใช่งบการเงินหรือกำไรสุทธิ

**สมมติฐานที่ต้องยืนยันก่อนเขียนโค้ด:** ร้านซื้อและขายเป็นหน่วยเดียวกัน (เช่น ชิ้น), ราคาทุนกรอกเป็นบาท/สตางค์ต่อหน่วยโดยไม่มี VAT แยก, ทุกใบรับของอ้างอิง PO, และเจ้าของร้านเป็นผู้ตรวจรับ ถ้าร้านรับสินค้าประเภทชั่งน้ำหนักหรือจ่ายเครดิตกับซัพพลายเออร์เป็นงานประจำ ให้ขยายสเปกก่อน pilot

## 2. แนวทางที่เลือก

| แนวทาง | ข้อดี | ข้อจำกัด |
| --- | --- | --- |
| รับสต๊อกเข้าอย่างเดียวแบบที่ mockup มี | ทำเร็ว | ไม่รู้ว่าสั่งอะไร ค้างรับเท่าไร หรือรับซ้ำจากเอกสารเดิมหรือไม่ |
| **PO + ใบรับของแยกกัน** | ตรวจจำนวนสั่ง/รับ/ค้างและเอกสารต้นทางได้; รับบางส่วนได้ | ต้องเพิ่มสถานะ PO และการตรวจคำขอชนกัน |
| ระบบจัดซื้อพร้อมเจ้าหนี้/การจ่ายเงิน | ครบวงจรบัญชีมากขึ้น | ขยายขอบเขตเงิน ภาษี และการกระทบยอดเกินความจำเป็นของโมดูลแรก |

เลือก **PO + ใบรับของ** โดย PO ไม่เปลี่ยนสต๊อกหรือเงินสด ส่วนการยืนยันใบรับของเท่านั้นที่เพิ่มสต๊อก ตัวเลขราคาจริงในใบรับของเก็บเป็นข้อมูลประวัติ แต่ยังไม่ปรับราคาขายหรือคำนวณกำไรอัตโนมัติ

## 3. ผู้ใช้และขั้นตอนทำงาน

1. `owner` สร้าง/ปิดใช้งานซัพพลายเออร์ เก็บชื่อที่แสดง เบอร์ติดต่อหรือช่องทางติดต่อที่จำเป็น และรหัสภายในที่ไม่ซ้ำ ไม่ลบซัพพลายเออร์ที่มี PO แล้ว
2. สร้าง PO สถานะ `draft`: เลือกซัพพลายเออร์ สินค้า จำนวนเต็มบวก ราคาทุนที่ตกลงต่อหน่วย และหมายเหตุ ถ้าสินค้ายังไม่มีใน catalog ให้สร้างสินค้าก่อนโดยไม่ถือว่าได้รับสต๊อก
3. ตรวจแล้วออก PO เป็น `issued` พร้อมเลขเอกสารถาวรและ snapshot ชื่อ/SKU/ราคาทุนขณะสั่ง หลังออกแล้วไม่แก้จำนวนหรือราคาเงียบ ๆ หากยังไม่รับของให้ยกเลิกและออกใบใหม่; หากรับไปแล้วให้ปิดยอดค้างพร้อมเหตุผล
4. เมื่อของมาส่ง เปิด PO และบันทึกใบรับของหนึ่งใบต่อการส่งหนึ่งครั้ง แสดงจำนวนสั่ง จำนวนรับสะสม และจำนวนค้างรับ กรอกจำนวนที่ **รับเข้าสต๊อก** และจำนวนที่ **ปฏิเสธ/เสียหาย** พร้อมเลขเอกสารส่งของหรือรหัสอ้างอิงที่ร้านกำหนด บันทึกราคาทุนจริงต่อหน่วย
5. ก่อนยืนยัน ระบบตรวจจำนวนที่ยังรับได้และแสดงส่วนต่างราคาจาก PO หากราคาจริงไม่ตรง ต้องระบุเหตุผล เจ้าของตรวจสินค้าแล้วกดยืนยัน ระบบสร้างใบรับของและ stock movements ใน transaction เดียว
6. PO คำนวณสถานะ `issued / partially_received / fully_received / closed_short / cancelled` จากเหตุการณ์ ห้ามยกเลิก PO ที่รับของแล้ว หากซัพพลายเออร์ส่งไม่ครบและจะไม่ส่งเพิ่ม ให้ `closed_short` พร้อมเหตุผล
7. เปิดดูหรือพิมพ์ PO และใบรับของเดิมได้โดยไม่สร้าง movement ใหม่ รายงานแสดงยอดสั่ง รับเข้า ปฏิเสธ และค้างรับแยกตาม PO/ซัพพลายเออร์/สินค้า

## 4. กติกาธุรกิจและ invariants

| รหัส | กติกา |
| --- | --- |
| PU01 | เฉพาะ `owner` ที่ใช้งานอยู่สร้าง/ออก/ยกเลิก/ปิด PO และยืนยันใบรับของ ตรวจสิทธิ์ที่ API ไม่อาศัยการซ่อนปุ่ม |
| PU02 | PO หนึ่งใบมีซัพพลายเออร์หนึ่งรายและอย่างน้อยหนึ่งสินค้า; สินค้าไม่ซ้ำใน PO; จำนวนสั่งเป็นจำนวนเต็มบวก; ราคาทุนหน่วยสตางค์ตั้งแต่ 0 ขึ้นไป |
| PU03 | `draft` แก้ไขได้แต่ไม่เปลี่ยนสต๊อกหรือเงิน; `issued` แล้วข้อมูลสั่งซื้อเป็น snapshot เปลี่ยนสถานะด้วยเหตุการณ์เท่านั้น |
| PU04 | `acceptedQty` และ `rejectedQty` ในใบรับต้องเป็นจำนวนเต็มไม่ติดลบ อย่างน้อยหนึ่งค่ามากกว่า 0; `Σ acceptedQty(PO line) ≤ orderedQty` ตรวจใหม่ใน write transaction |
| PU05 | จำนวนที่ปฏิเสธไม่เพิ่มสต๊อกและไม่ลดจำนวนค้างรับ เพราะยังอาจรอของทดแทน; `outstandingQty = orderedQty − Σ acceptedQty` |
| PU06 | จำนวนรับจริงที่ต่างจาก PO ไม่อนุญาตให้รับเกินโดยเงียบ ๆ หากต้องเพิ่มจำนวน ให้สร้าง PO ใหม่; ราคาทุนจริงที่ต่างจาก PO ทำได้เฉพาะพร้อมเหตุผลและ snapshot ราคาเดิม/ใหม่ |
| PU07 | ยืนยันใบรับแล้วสร้าง `goods_receipt`, lines, stock movements จำนวนบวกเฉพาะ accepted, stock balances, audit และผล idempotency ใน SQLite transaction เดียว |
| PU08 | request key เดิม + payload เดิมคืนใบรับเดิม; key เดิม + payload ต่างกันคืน `409 IDEMPOTENCY_CONFLICT`; key ใหม่ที่พยายามรับเกินค้างต้องถูกปฏิเสธ |
| PU09 | ใบรับของที่ยืนยันแล้วแก้หรือลบผ่านแอปไม่ได้ หากนับผิดต้องใช้ stock adjustment พร้อมเหตุผลและอ้างอิงใบรับ ไม่ย้อนแก้ประวัติการรับ |
| PU10 | การสร้าง/รับ PO ไม่บันทึกเงินสดเข้าหรือออกลิ้นชัก หากจ่ายเงินสดจากลิ้นชักจริง ให้ใช้ `cash out` ของกะพร้อมเลขอ้างอิง PO และกระทบยอดเอง โมดูลนี้ไม่ระบุว่า PO จ่ายแล้ว |
| PU11 | จำนวนเงินทุกช่องเป็น integer สตางค์ ตรวจ safe integer ของ `quantity × unitCostCents` และผลรวม; timestamp เก็บ UTC แสดงวันตาม `Asia/Bangkok` |
| PU12 | `cancelled` ได้เมื่อยังไม่มีใบรับของแม้แต่ใบเดียว; `closed_short` ได้เมื่อออก PO แล้วและยอดรับต่ำกว่ายอดสั่ง ต้องมีเหตุผล; PO ที่ปิดแล้วรับเพิ่มไม่ได้ |

คำสั่งสร้าง/ออก/ยกเลิก/ปิด PO และยืนยันใบรับต้องมี request key ตามกลไก idempotency เดิม ส่วนรหัสซัพพลายเออร์ที่ไม่ซ้ำช่วยกันการสร้างซ้ำจากคำตอบสูญหาย

สถานะ `fully_received` คำนวณเมื่อทุก line มี `outstandingQty = 0` ไม่ใช้ยอดปฏิเสธมาหักค้างรับ สินค้าที่เคยอยู่ใน PO ให้ปิดจำหน่ายใน catalog ได้ แต่ข้อมูลเดิมต้องยังอ่านได้

## 5. โมเดลข้อมูลและ API ที่เสนอ

สคีมาบน production stack ตาม [แผนเตรียมระบบขายจริง](production-readiness.md) ใช้ FK/CHECK/UNIQUE และ transaction จริง ไม่เก็บ PO ใน `localStorage` เมื่อขายจริง

| ตาราง | ฟิลด์หลัก | ข้อบังคับ |
| --- | --- | --- |
| `suppliers` | `id`, `code`, `name`, `contact`, `active`, timestamps | `code` ไม่ซ้ำหลัง normalize; ไม่ลบแถวที่ถูกอ้างอิง |
| `purchase_orders` | `id`, `po_no`, `supplier_id`, `status`, `created_by`, `issued_at`, `closed_at`, `close_reason` | เลข PO ถาวรไม่ซ้ำ; FK; สถานะเปลี่ยนตามกติกา |
| `purchase_order_lines` | `id`, `po_id`, `product_id`, `sku_snapshot`, `name_snapshot`, `ordered_qty`, `agreed_unit_cost_cents` | `UNIQUE(po_id, product_id)`; จำนวนบวก; ราคาทุนไม่ติดลบ |
| `goods_receipts` | `id`, `receipt_no`, `po_id`, `delivery_ref`, `received_at_utc`, `received_by` | เลขใบรับไม่ซ้ำ; เลขอ้างอิงการส่งไม่ซ้ำภายใน PO: `UNIQUE(po_id, delivery_ref)` |
| `goods_receipt_lines` | `id`, `receipt_id`, `po_line_id`, `accepted_qty`, `rejected_qty`, `actual_unit_cost_cents`, `cost_variance_reason` | `UNIQUE(receipt_id, po_line_id)`; อย่างน้อยหนึ่งจำนวนบวก |
| `stock_movements` | เพิ่มชนิด `purchase_receipt` และ FK/reference ไป `goods_receipt_line` | หนึ่ง accepted line สร้าง movement บวกหนึ่งรายการ; ไม่มี movement สำหรับ rejected |
| `idempotency_requests` / `audit_log` | เพิ่ม action สำหรับ PO/receipt | เก็บ payload hash, ผลคำขอ และผู้ทำรายการ |

`delivery_ref` ต้องระบุทุกใบรับ ถ้าซัพพลายเออร์ไม่มีเลขเอกสาร ให้เจ้าของใช้รหัสรับของภายในที่ติดกับการส่งครั้งนั้น การตรวจ unique ภายใน PO ช่วยกันรับซ้ำจากเอกสารเดียวกัน แต่ไม่สามารถรู้เองว่ารหัสคนละตัวเป็นของส่งซ้ำ จึงยังต้องเทียบเอกสารและของจริง

API ตัวอย่าง (ปรับชื่อ route ให้ตรง convention ของ API หลักเมื่อพัฒนา):

| Endpoint | หน้าที่ |
| --- | --- |
| `GET/POST /api/suppliers` | ค้นและสร้างซัพพลายเออร์; แก้ไข/ปิดใช้งานตามสิทธิ์ owner |
| `GET/POST /api/purchase-orders` | ค้นและสร้าง PO draft |
| `GET /api/purchase-orders/{id}` | ดู PO, รายการรับ, จำนวนค้าง และสถานะ |
| `POST /api/purchase-orders/{id}/issue` | ออก PO ที่ตรวจแล้ว |
| `POST /api/purchase-orders/{id}/cancel` / `close-short` | เปลี่ยนสถานะพร้อมเหตุผลตามกติกา |
| `POST /api/goods-receipts` | ยืนยันรับของโดยอ้าง PO/PO lines, request key, delivery ref, accepted/rejected, actual cost |
| `GET /api/goods-receipts/{id}` | ดู/พิมพ์ใบรับเดิม |
| `GET /api/requests/{requestKey}` | กู้ผลคำขอเดิมเมื่อ response หาย ตามระบบ idempotency ของ POS |

ข้อผิดพลาดหลัก: `PO_NOT_FOUND`, `PO_NOT_ISSUED`, `PO_CLOSED`, `PRODUCT_NOT_IN_PO`, `RECEIPT_QUANTITY_EXCEEDED`, `DUPLICATE_DELIVERY_REF`, `COST_VARIANCE_REASON_REQUIRED`, `FORBIDDEN`, `IDEMPOTENCY_CONFLICT` และข้อผิดพลาดการบันทึกของ POS เดิม ทุกข้อผิดพลาดต้องไม่มีการเพิ่มสต๊อกหรือสร้างใบรับบางส่วน

## 6. ตัวเลขและรายงาน

```text
ค้างรับต่อ PO line = จำนวนสั่ง − ผลรวมจำนวนรับเข้าสต๊อก
ยอดมูลค่าสั่งตาม PO = Σ (จำนวนสั่ง × ราคาทุนที่ตกลง)
ยอดมูลค่ารับจริง = Σ (จำนวนรับเข้าสต๊อก × ราคาทุนจริง)
```

ยอดมูลค่ารับจริงเป็นประวัติการซื้อของที่รับแล้ว **ไม่ใช่** ต้นทุนขายหรือกำไร และไม่รวมของที่ปฏิเสธ รายงานการรับจัดตามวันที่รับจริงใน `Asia/Bangkok`; รายงานค้างรับดูยอดปัจจุบันของ PO ที่ยังเปิด ซัพพลายเออร์และสินค้าเป็นตัวกรอง การปรับสต๊อกภายหลังเป็นเหตุการณ์ใหม่ ไม่ย้อนเปลี่ยนใบรับหรือมูลค่ารับเดิม

ตัวอย่าง: สั่งน้ำ 10 ชิ้น ราคาทุน 12 บาท/ชิ้น รอบแรกมาส่ง 7 ชิ้น ตรวจรับได้ 6 ปฏิเสธ 1: สต๊อก +6, มูลค่ารับ 72 บาท, ค้างรับ 4 ชิ้น รอบถัดมารับได้อีก 4: สต๊อกเพิ่มอีก 4, ค้างรับ 0, PO เป็น `fully_received` หากราคาในรอบถัดไปเป็น 13 บาท/ชิ้น ต้องระบุเหตุผลส่วนต่างและมูลค่ารับรอบนั้นเป็น 52 บาท

## 7. ความขัดข้องและการทำงานร่วมกับ POS เดิม

- **คำตอบใบรับหาย:** UI เก็บ request key/payload ค้างข้าม reload ใช้ key เดิมค้นผลก่อนเริ่มรับอีกใบ หาก commit แล้ว การส่งซ้ำคืนใบรับเดิม ไม่เพิ่มสต๊อกซ้ำ
- **รับพร้อมกันสองคำขอ:** ตรวจค้างรับและบันทึกใน write transaction เดียว SQLite serialized writer ต้องทำให้รวมรับไม่เกิน PO; ทดสอบกรณีแข่งขันจริง
- **รับสต๊อกแบบเดิม:** คงเมนูรับ/ปรับยอดที่มีอยู่สำหรับยอดตั้งต้นหรือเหตุพิเศษ แต่รายการซื้อจากซัพพลายเออร์ต้องผ่านใบรับ PO; UI และ movement ต้องแยกชนิด `manual_receive` จาก `purchase_receipt` เพื่อไม่ให้ยอดเดียวกันถูกบันทึกสองครั้ง
- **คืนสินค้าจากลูกค้า:** โมดูลคืนสินค้าเพิ่มสต๊อกผ่าน movement ของ return เท่านั้น ไม่เกี่ยวกับยอดค้างรับของ PO
- **เงินสด/กะ:** PO และใบรับไม่แตะยอดกะ หากซื้อเงินสดจากลิ้นชักจริง ให้ลงเงินนำออกแยกและใส่เลข PO ในเหตุผล ห้ามระบบหักเงินอัตโนมัติจากมูลค่า PO
- **backup/restore:** PO, receipts, stock movements, balance, request results และ audit ต้องอยู่ใน snapshot เดียวกัน หลัง restore เทียบใบรับล่าสุดกับของจริง/เอกสารส่งของก่อนรับต่อ
- **mockup:** หากทดลอง UX ใน `mockup/` ต้อง migration ข้อมูลตัวอย่างที่มีอยู่โดยไม่ล้างข้อมูล แต่ผลทดสอบ `localStorage` ไม่ใช้แทน transaction/authorization/durability ของ production

## 8. ลำดับส่งมอบและเกณฑ์ตรวจรับ

1. ตรวจ flow และแบบหน้าจอใน mockup เดิม: ซัพพลายเออร์, PO, รับบางส่วน, ใบรับ, ค้างรับ และประวัติ movement
2. บน production POS ที่มี API/SQLite แล้ว ทำ schema migration และ service สำหรับ supplier/PO/receipt พร้อม constraints, transaction, idempotency และ audit
3. เชื่อม UI/รายงาน ทดสอบ integration กับ SQLite จริงและ browser flow บนอุปกรณ์ร้าน รวม response หาย, คำขอชนกัน, ดิสก์เต็ม และ restore
4. ทดลอง PO จริงอย่างน้อยหนึ่งใบที่ส่งของหลายครั้ง กระทบยอดสินค้าในร้านกับเอกสารซัพพลายเออร์ก่อนเปิดใช้งาน

| กรณีตรวจรับ | ผลที่ต้องได้ |
| --- | --- |
| ออก PO 10 ชิ้นโดยยังไม่รับ | สต๊อกและเงินสดไม่เปลี่ยน; ค้างรับ 10 |
| รับ 6 ดี + 1 เสียจากการส่ง 7 | สต๊อก +6; ค้างรับ 4; rejected 1 ในประวัติ; มูลค่ารับตาม 6 ชิ้น |
| รับอีก 4 ในใบรับใหม่ | สต๊อกเพิ่มอีก 4; ค้างรับ 0; PO `fully_received` |
| ส่งรับเกินค้าง 1 ชิ้น หรือสินค้าไม่ได้อยู่ใน PO | ปฏิเสธทั้งคำขอ ไม่มี movement/receipt บางส่วน |
| ราคาทุนจริงต่าง PO | ขอเหตุผล; เก็บ snapshot ราคาจริงและเดิม; ไม่เปลี่ยนราคาขาย |
| ส่ง key/payload เดิมซ้ำหลัง response หาย | ได้ใบรับเดิม สต๊อกเพิ่มครั้งเดียว; payload ต่างด้วย key เดิม conflict |
| สองคำขอพร้อมกันรับค้าง 4 ชิ้นคำขอละ 4 | สำเร็จได้เพียงหนึ่งคำขอ อีกคำขอถูกปฏิเสธ; รวมรับไม่เกิน 4 |
| delivery ref เดิมของ PO เดิมด้วย key ใหม่ | ปฏิเสธเป็นเอกสารส่งซ้ำ ไม่เพิ่มสต๊อก |
| cashier เรียก API ตรง / PO ปิดแล้ว / disk failure | ปฏิเสธหรือ rollback ครบ ไม่มีใบรับและสต๊อกบางส่วน |
| ยกเลิก PO ที่รับไปแล้ว | ปฏิเสธ; ใช้ `closed_short` พร้อมเหตุผลหากไม่รอของเพิ่ม |
| ซื้อเงินสด 120 บาทจากลิ้นชัก | PO/receipt ไม่เปลี่ยนเงินกะ; cash out 120 บาทที่บันทึกแยกจึงลดเงินคาดหวัง 120 บาท |

**เกณฑ์พร้อมใช้จริง:** ทุกหน่วยที่เพิ่มในสต๊อกย้อนถึงใบรับและ PO ได้, ยอดรับสะสมไม่เกินยอดสั่ง, รายงานค้างรับตรงกับเอกสาร, คำขอซ้ำไม่รับของซ้ำ, สิทธิ์ฝั่ง API บังคับได้ และผ่านการทดสอบกับ SQLite/อุปกรณ์ร้านจริงก่อนใช้กับสินค้าเงินจริง
